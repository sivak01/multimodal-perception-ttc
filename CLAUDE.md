# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A multi-sensor (camera + radar + LiDAR) fusion research pipeline built on the **nuScenes v1.0-mini** dataset. It reconstructs, from raw sensor logs, per-object tracks in a global frame, fuses them across sensors, and computes Time-To-Collision (TTC) estimates for evaluation against ground-truth annotations. There is no application code — the entire pipeline is a sequence of numbered Jupyter notebooks, each a self-contained pipeline stage that reads the previous stage's output from disk and writes its own.

There is no test suite, linter, or build system — correctness is checked via the notebooks themselves (see Step 7 below) and by re-running stages.

## Running the pipeline

Notebooks must be run **in numeric order**, top to bottom, since each stage's outputs are the next stage's inputs (all paths flow through `config.py`, see below). There's no CLI entry point — open notebooks in Jupyter/VS Code and run all cells, or execute headlessly:

```bash
jupyter nbconvert --to notebook --execute --inplace "Step_0_Dataset_Preparation.ipynb"
```

Pipeline order:

| Stage | Notebook | Purpose |
|---|---|---|
| 0 | `Step_0_Dataset_Preparation.ipynb` | Indexes nuScenes samples; writes `samples_index.json`, the master index every downstream step reads |
| 1.1 | `Step_1_1_Camera_Preprocessing.ipynb` | Camera calibration/intrinsics per sample; imports `project_point_to_camera()` from `src/geometry.py` |
| 1.2 | `Step_1_2_Radar_Parsing.ipynb` | Parses raw radar point clouds per channel |
| 1.3 | `Step_1_3_LiDAR_Parsing.ipynb` | Parses raw LiDAR point clouds (N×7 arrays: point + derived fields) |
| 2.1 | `Step_2_1_LiDAR_Processing.ipynb` | Ground-plane removal (Open3D `segment_plane`) + DBSCAN clustering |
| 2.2 | `Step_2_2_Radar_Processing.ipynb` | Radar filtering (dynamic-property filter) + feature extraction (raw + ego-compensated velocity) |
| 2.3 | `Step_2_3_YOLOv5.ipynb` | YOLO 2D object detection on camera frames (uses `ultralytics`, weights in `yolov8n.pt`) |
| 2.3.1 | `Step_2_3_1_YOLO_Global_Projection.ipynb` | Lifts each 2D YOLO box to a 3D global-frame position by fusing with LiDAR |
| 2.3.2 | `Step_2_3_2_YOLO_Monocular_Depth.ipynb` | Lifts each 2D YOLO box to 3D using similar-triangles depth-from-height (no LiDAR) — a true monocular-only baseline; see below |
| 3.1 | `Step_3_1_LiDAR_Fusion.ipynb` | Multi-frame LiDAR tracking (nearest-neighbor / Hungarian assignment via `scipy.optimize.linear_sum_assignment`), global frame |
| 3.2 | `Step_3_2_Radar_Fusion.ipynb` | Multi-frame radar tracking, same family as 3.1; clusters multi-blip radar returns into one detection per object before tracking |
| 3.3 | `Step_3_3_Camera_Tracker.ipynb` | Multi-frame camera tracking (LiDAR-assisted depth), global 3D nearest-neighbor across all 6 cameras |
| 3.4 | `Step_3_4_Camera_Mono_Tracker.ipynb` | Same tracker design as 3.3, reading Step 2.3.2's monocular-only detections instead |
| 4 | `Step_4_Fusion.ipynb` | Fuses LiDAR/radar/camera tracks into unified tracks — runs its own per-sensor UKF/CTRV smoothing on each contributing sensor track first, then merges the smoothed states (state-level fusion; see below). Does not include the camera-mono baseline. |
| 5 | `Step_5_TTC.ipynb` | UKF + CTRV motion model → TTC estimate per track for LiDAR/radar/camera/camera-mono; the fused dataset already carries state-fused velocity from Step 4, so it skips straight to TTC instead of re-filtering |
| 6 | `Step_6_Visualization.ipynb` | Trend plots + evaluation metrics against nuScenes `sample_annotation` ground truth |
| 7 | `Step_7_Pipeline_Audit.ipynb` | Read-only audit: walks Steps 0–6 checking input/output counts and known-bug regressions at every stage; does not modify any output |
| 8 | `Step_8_BEV_Fusion_Video.ipynb` | Terminal visualization stage: renders a per-sample Bird's-Eye-View (all sensors + fused TTC) next to the real `CAM_FRONT` frame, and encodes one MP4 per scene; see below |
| — | `Validate_Step_2_3_1.ipynb` | Standalone validator for Step 2.3.1's 3D projections |

Each notebook's first markdown cell documents its own **Input / Outputs / Used by** table — read that cell before modifying a stage, since output schemas are contracts downstream notebooks depend on exactly (e.g. LiDAR/radar tracks are tuple-format, camera tracks are dict-format — Step 4 handles both explicitly).

## Architecture

**`config.py` is the single source of truth for all paths.** Every notebook starts by importing from it (e.g. `from config import STEP0_DIR, STEP1_DIR, ...`). It anchors `PROJECT_ROOT`/`BASE_DIR` to its own file location (not the Jupyter CWD), points `DATA_ROOT` at the nuScenes dataset, and derives one output subdirectory per stage (`STEP0_DIR` … `STEP6_DIR`) under `output/`. **Change dataset/output locations only in `config.py`** — never hardcode paths inside a notebook.

**`src/geometry.py`** holds the sensor-to-global and global-to-camera coordinate transform math (`transform_matrix`, `point_to_global`, `points_to_global`, `project_point_to_camera`, `global_points_to_camera`). This used to be copy-pasted independently into Steps 1.1, 2.3.1, 3.1, and 3.2; those notebooks now `from src.geometry import ...` instead. Step 2.3.2 (monocular depth baseline) also imports `point_to_global()` from here, to lift its similar-triangles depth estimate into the global frame the same way every other stage does. Step 3.1 imports `point_to_global` under the alias `centroid_to_global` to match its existing call sites. If you touch this file, all four notebooks are affected — re-run them to confirm. `GlobalFrameTracker` (Step 3.1 vs 3.2), `compute_ttc` (Step 5 vs Step 6), and now the UKF/CTRV core (`merwe_sigma_points`/`ctrv_process`/`ukf_predict`/`ukf_update`, Step 4 vs Step 5) are similarly duplicated but were *not* unified — their implementations have diverged enough (radar-specific tuning, ground-truth-specific lookups, Step 4's per-sensor-track smoothing vs Step 5's per-dataset TTC runner) that merging them needs a closer read than a mechanical extraction; treat that as a known follow-up, not an oversight. Verified by executing all four notebooks end-to-end (`python -m nbconvert --to notebook --execute ...` — note `python -m jupyter nbconvert` silently exits 1 with no output on at least one Windows setup seen in this repo's history; call `nbconvert` as a module directly instead); Step 3.1's per-run diagnostic numbers matched the pre-refactor baked-in output exactly.

**Step 3.1, Step 3.2, Step 3.3, and Step 4 used to not be idempotent — now fixed.** `save_tracks()` (all three trackers) writes `track_<uuid4>.json` with a fresh random id every run, and previously never cleared its output directory first, so re-running any of them without deleting that directory first accumulated duplicate track files on top of the previous run's (confirmed: re-running Step 3.1 once turned 4930 LiDAR track files into 9860). Each of the four notebooks' setup cells now `shutil.rmtree()`s its own output directory before recreating it, so a plain re-run always produces a clean single-run result — no manual deletion needed anymore.

**This already silently happened once, undetected, and contaminated a committed evaluation table.** The `evaluation_metrics.csv` "after" numbers referenced below (and the "fusion got worse" finding) were computed on top of Step 3 output that had accumulated across two runs without clearing: LiDAR's on-disk `8072` = `4930` stale pre-declutter-fix tracks + `3142` from the real post-fix run (confirmed exactly: `4930+3142=8072`, and `3142` matches the notebook's own committed cell output at commit `bac3e4e`); radar's on-disk `13760` was ~8x the real single-run count (~1698). Camera happened to only ever run once (`1131` on disk = `1131` in the committed cell output) so it's clean. This was only caught by chance while diagnosing an unrelated track-count change during the scene-boundary-isolation fix below — **treat every number in the "fusion got worse" table as unverified until Steps 4–6 are re-run on a freshly-cleared, single-run Step 3 output** (Step 3 was re-cleared and re-run clean as of that fix: LiDAR 3152, radar 1693, camera 1131 saved tracks).

Data flow is entirely file-based: each stage reads JSON/CSV/NPY files written by the prior stage under `output/step_N/...` and writes its own under `output/step_(N+1)/...`; there is no in-memory hand-off between notebooks. Key artifacts:
- `output/step_0/samples_index.json` — master sample index, read by nearly every later stage. Each entry: `sample_token`, `scene_token`, `scene_name`, `timestamp_us` (authoritative `sample['timestamp']`, not any one sensor's own capture time — see fix below), `prev_token`/`next_token` (`""` at scene start/end), `folder`, `sensors`.
- `output/step_1/lidar/<sample>/lidar_raw.npy` — per-point LiDAR array (N×7).
- `output/step_2/yolo_global/<sample>/<camera>.json` — YOLO detections lifted to 3D global coordinates (LiDAR-assisted depth).
- `output/step_2/yolo_mono/<sample>/<camera>.json` — YOLO detections lifted to 3D via similar-triangles depth-from-height (no LiDAR); see below.
- `output/step_3/{lidar,radar,camera,camera_mono}/track_<id>.json` — per-sensor multi-frame tracks in the global frame.
- `output/step_4/fused/track_<id>.json` and `fused_tracks_all.csv` — fused multi-sensor tracks; `x,y,z` and `vx,vy` are already state-level fused (see below), not raw positions.
- `output/step_5/ttc_{lidar,radar,camera,fused}.csv` — same schema across sensors, directly comparable.

`html/` holds rendered HTML exports of each notebook (for viewing without Jupyter) and is regenerated from the notebooks, not hand-edited. `archive/` and `Old Codes/` hold prior notebook revisions and an old zipped copy of the project kept for reference — do not treat them as current; the root-level `Step_*.ipynb` files are canonical. `assets/` holds a small set of result images copied from `output/` and committed for the README — it's curated by hand, not regenerated automatically, so re-copy into it manually after a pipeline run if you want the README images refreshed.

`output/`, `DATA SET/`, `html/`, `archive/`, and `Old Codes/` are gitignored (see `.gitignore`); `assets/` is intentionally not.

## Known data-quality fixes and their measured effect

These were identified by auditing pipeline behavior against actual code (not assumed), then verified by re-running the affected notebooks end-to-end:

- **Authoritative sample timestamp + scene metadata** (`Step_0_Dataset_Preparation.ipynb`): the master index's timestamp was `list(sensor_meta["sensor_channels"].values())[0]['timestamp']` — an arbitrary sensor's own capture time (whichever channel happened to be first in `sample['data']`'s dict order), off from the true sample timestamp by up to ~45ms. Now uses the authoritative `sample['timestamp']`, stored as `timestamp_us`. Also added `scene_token`/`scene_name`/`prev_token`/`next_token` per sample (needed by the scene-boundary-isolation fix below), a 12-channel presence check, and an `_source_channel` tag on `ego_pose.json` recording which sensor's pose was used. The `timestamp_us` rename was cascaded to every downstream reader (Steps 3.1, 3.2, 4, 5, 6) so nothing silently breaks on `KeyError: 'timestamp'`.
- **Radar declutter** (`Step_2_2_Radar_Processing.ipynb`): the `dyn_prop` filter only excluded value `7`; the nuScenes enum has several other "not really moving" values (`1` stationary, `3` stationary candidate, `4` unknown, `5` crossing stationary). Now keeps only `{0, 2, 6}` (moving/oncoming/crossing-moving — the devkit's own recommended set for "moving objects only"). Effect: ~158 → ~27.5 kept detections/sample. **Superseded later** (see "Radar declutter filter relaxed" further down this file): `{0, 2, 6}` turned out to also be discarding real, accurate, GT-annotated stationary objects (parked cars especially) alongside the genuine clutter it was built to remove — the current filter is `{0, 1, 2, 3, 6, 7}`.
- **Radar blip clustering** (`Step_3_2_Radar_Fusion.ipynb`): one real object produces 3–8 separate radar blips; there was no grouping step before tracking. DBSCAN (`RADAR_CLUSTER_EPS = 1.5m`, `min_samples=1`) now groups blips into one centroid per object before they reach `GlobalFrameTracker`.
- **LiDAR cluster shape filter** (`Step_2_1_LiDAR_Processing.ipynb`, optional/lowest-priority): discards DBSCAN clusters whose bounding box is implausible for a vehicle/pedestrian (`CLUSTER_MIN_HEIGHT_M`/`MAX_HEIGHT_M`/`MAX_HORIZONTAL_EXTENT_M`/`MAX_ASPECT_RATIO` in the cell) — filters out curbs, hedges, wall fragments. Effect: ~66.3 → ~44.0 clusters/sample. Also hardened: `skipped_samples` tracking (same pattern as Step 1.3) for missing `lidar_raw.npy`, and a strengthened completion assertion cross-checked against Step 1.3's own row count (`output/step_1/lidar_summary.csv`) instead of only checking `summary_rows` is non-empty. **`CLUSTER_MAX_HORIZONTAL_EXTENT_M=15.0` checked against a real worst case, not just assumed correct**: `sample_0023` has the most shape-discards of any sample (55). Of those, only 2 were rejected specifically for `too wide/long`, and neither looks like a real vehicle — one is 21.3m long with 13,255 points (more LiDAR returns than most entire scenes' non-ground clouds combined; almost certainly a DBSCAN-merged wall/building fragment, not a single object), the other is a near-square 16.1m×9.7m footprint at only 2.18m tall (real buses/trucks are long and *narrow*, ~2.5–3m wide, not this). The other 53 discards in that sample are all genuinely flat (`dz<0.4m` — road paint, curbs, debris). Conclusion: don't loosen this threshold based on this evidence — doing so would let implausible merged blobs back into the tracked-object pool, not recover missed buses/trucks. Separately, this same check surfaced a real but out-of-scope issue: even some *kept* clusters in this sample look like under-segmented multi-object blobs (e.g. a kept 12.4m×13.6m×3.6m cluster) — DBSCAN's `eps`/`min_samples` may be too permissive in dense scenes; flagged as a follow-up, not fixed here.
- **YOLO class/confidence filter** (`Step_2_3_YOLOv5.ipynb`): was `model.classes = None` (all 80 COCO classes) at `conf=0.25`. Now `model.classes = [0,1,2,3,5,7]` (person/bicycle/car/motorcycle/bus/truck only) at `conf=0.35`.
- **Fusion merge Bug A** (`Step_4_Fusion.ipynb`, `merge_frame_observations()`): nothing prevented two detections from the *same* sensor from being merged together (e.g. two real pedestrians seen only by LiDAR could get squashed into one). Fixed: the union edge now requires different sensors.
- **Fusion merge Bug B**: the old pass was greedy (single forward scan), not a real union-find, so a chain of 3+ pairwise-close detections split into multiple clusters instead of one. Fixed with a proper disjoint-set union — verified by unit test (3 collinear points, 2m apart, `merge_thresh=3` → now one cluster, not `{p0,p1}` + `{p2}`).
- **Fusion averaging weighted by sensor trust**: was a flat `np.mean` over merged positions, treating LiDAR/radar/camera as equally accurate. `SENSOR_TRUST_WEIGHT = {"lidar": 44, "radar": 4, "camera": 1}` (inverse-variance-style, from ~0.15m/~0.5m/~1.0m assumed position noise) now weights the merge — verified by unit test (LiDAR+radar 1m apart merges to 91.7% toward LiDAR, as the weight ratio implies).
- **Evaluation scorecard** (`Step_6_Visualization.ipynb`, `compute_evaluation_metrics()`): `n_tracks_matched`/`n_tracks_total` were computed and printed to console but never added to the returned dict, so they never reached `evaluation_metrics.csv` — now included as `N_Tracks_Total`/`N_Tracks_GT_Matched`. The console message *"tracks found a GT lock at their first frame"* was misleading — `match_predictions_to_ground_truth()` actually retries the lock attempt every frame until one succeeds, not only frame 1; message text corrected. Added a sanity check that warns if two sensors report suspiciously identical `n_matched_pairs`.
- **`src/geometry.py` hardening** (additive only — no existing math changed): `tests/test_geometry_projection.py` cross-validates `project_point_to_camera()` against nuScenes devkit's own independent `Box.translate/rotate` + `view_points()` chain on real ground-truth boxes across 5 samples/2 scenes/2 cameras, including a dedicated high-yaw-rate turn sample (179° between consecutive samples) — all pass at 0.0000px deviation. Added a non-fatal frame-contract warning to `global_points_to_camera()` for suspiciously local-looking input (mean `|xyz|` below a threshold); calibrated to 100m, not the naively-plausible 5m, since this dataset's real local LiDAR sweeps average ~10m mean magnitude (median ~6m) while its global frame sits around 1100–1250m — a 5m cutoff would never actually fire. Added `project_points_to_camera_batch()` (precomputes one combined 4×4 transform instead of rebuilding per point) as a batch-safe alternative to the scalar function for any future per-point-in-a-loop reuse; verified identical to the scalar function on 100 real points (0.0000px difference). Note: as of this fix, `src/geometry.py`'s projection functions are wired into Steps 1.1, 2.3.1, 3.1, and 3.2 only — `Step_4_Fusion.ipynb` does not import from it at all (grep-confirmed), despite Step 1.2's markdown once implying otherwise (now corrected there too).
- **Step 1.2 hardening** (`Step_1_2_Radar_Parsing.ipynb`): `samples_index` load moved into Cell 1 so the diagnostic cell (Cell 2) is truly optional/deletable without breaking the main parse loop (verified: deleting it and re-running produces identical output). Added a `failed_channels` aggregate tracker writing `parse_failures.json` (written even when empty). Corrected a false markdown claim that this notebook "reuses `project_point_to_camera()` from Step 1.1" — it never has; the per-point calibration it stores is for a downstream notebook to consume.
- **Scene-boundary isolation** (`Step_3_1_LiDAR_Fusion.ipynb`, `Step_3_2_Radar_Fusion.ipynb`, `Step_3_3_Camera_Tracker.ipynb`): all three trackers process every sample in one continuous loop with no notion of nuScenes scene boundaries (v1.0-mini has 10 scenes, i.e. 9 boundaries across the 404 samples), so nothing stopped a track from associating the last frame of one scene with the first frame of the next. Each tracker (`GlobalFrameTracker`, `ClassAwareGlobalTracker`) now takes a `scene_name` argument, and at a scene change force-finalizes every active track and starts a fresh, empty track table — no ID, motion state, or last-known-position carried across. Each also logs every accepted association as `(prev_sample_id, prev_scene, curr_sample_id, curr_scene)` and asserts zero cross-scene entries at the end of its run. Verified two ways (in-run assertion + an external scan of every saved track's sample_ids against `samples_index.json`'s `scene_name`): 0 cross-scene associations, 0 scene-spanning tracks, on all three sensors. Note this was already true *before* the fix too — at `ASSOC_DIST_THRESHOLD=3.0m` two different scenes are never spatially/temporally close enough to false-match — so this is a correctness/defense-in-depth fix, not one that was visibly corrupting prior results.
- **Step 3/4 non-idempotency fix** (`Step_3_1_LiDAR_Fusion.ipynb`, `Step_3_2_Radar_Fusion.ipynb`, `Step_3_3_Camera_Tracker.ipynb`, `Step_4_Fusion.ipynb`): each stage's setup cell now `shutil.rmtree()`s its own output directory before recreating it, so a re-run always produces a clean single-run result instead of accumulating duplicate `track_<uuid4>.json` files on top of the previous run's (see the non-idempotency note above — this fixes it rather than just documenting it).
- **`timestamp_us` cascade was incomplete** (`Step_5_TTC.ipynb`, `Step_6_Visualization.ipynb`): despite the Step 0 fix above claiming the `timestamp_us` rename was "cascaded to every downstream reader," both notebooks' own duplicated ego-position-lookup cells (`ego_pos_by_sample`, used to compute the ego vehicle's global position/velocity for TTC) still read the old `info["timestamp"]` key, which no longer exists on `samples_index.json` entries. Both crashed with `KeyError: 'timestamp'` on a clean re-run. Fixed by changing both to `info["timestamp_us"]` — a one-line change in each notebook's cell.
- **Sensor-aware UKF measurement noise** (`Step_5_TTC.ipynb`): the UKF's measurement noise `R` was a single fixed `np.diag([0.5, 0.5])` regardless of which sensor(s) produced a given fused point — and `fused_df` didn't even carry the `sensors` column into the TTC pipeline, so the filter had no way to know a frame came from noisy radar vs. precise LiDAR. Added `measurement_noise_for(sensors_field)`, deriving `R` from the same `SENSOR_TRUST_WEIGHT` values Step 4's merge already uses (combined variance of an inverse-variance-weighted merge is `1 / sum(weights)`), applied per-row inside the UKF loop. Effect on fused: MAE 4.05→3.84, RMSE 8.32→8.12, Good_pct 44.8→46.0. Single-sensor datasets barely moved, as expected (homogeneous source, only the absolute noise value changed).
- **State-level fusion, replacing per-frame raw-position averaging** (`Step_4_Fusion.ipynb`, `Step_5_TTC.ipynb`): previously, Step 4 merged raw single-frame positions across sensors (weighted average), and Step 5 then ran one UKF over that merged stream from scratch — so the filter had no track history and started blind every time sensor composition changed frame-to-frame (confirmed: 25.8% of fused tracks switch composition at least once). Step 4 now runs the same UKF/CTRV model independently and continuously on each contributing sensor's own track *before* any cross-sensor merge (new cell, `smooth_track_states()`), then `merge_frame_observations()` combines each sensor's already-smoothed `(x, y, vx, vy)` state — not raw positions — still trust-weighted by `SENSOR_TRUST_WEIGHT`. `fused_tracks_all.csv` now carries real `vx`/`vy` columns. Step 5's fused path (`run_ttc_pipeline_state_fused()`) no longer re-filters this stream at all — it computes TTC directly from the already-fused velocity, since re-running a from-scratch UKF on already-fused-and-smoothed data would just reintroduce the same blind-restart problem. Effect on fused: MAE 3.84→3.64, RMSE 8.12→7.82, Good_pct 46.0→49.3.
- **`FusedTracker` next-frame prediction used a noisier estimate than it had to** (`Step_4_Fusion.ipynb`): frame-to-frame association predicted a track's next position from a fresh 2-point finite-difference of its own last two raw positions, discarding the already-smoothed per-sensor UKF `vx`/`vy` each point carries (from the state-level fusion fix above). A bad prediction pushed the real next detection outside `FUSION_DIST_THRESHOLD=3.0m`, causing Hungarian to miss a valid association and spawn a duplicate track for an object that never left view — confirmed directly by tracing one real pedestrian (see the track-fragmentation investigation below): two fused tracks were found coexisting for the same object across frames 90–93, positions diverging to 4m+ apart. Fixed to prefer the point's own smoothed `vx`/`vy` for prediction, falling back to the old finite-difference only if a point ever lacks a smoothed velocity (defensive, not currently reachable — every point Step 4 produces already carries one). `dt_now` already used real timestamps, not nominal spacing, so no change was needed there. Effect: fused `N_Tracks_Total` 4138→3918 (−5.3%); the traced pedestrian's fragment count dropped 10→4 with no more overlapping duplicates. MAE/RMSE/Good_pct barely moved (3.64→3.63 / 7.82→7.79 / 49.3→49.5) — expected, since this fixes track *identity continuity*, not per-point position/velocity accuracy. `N_Tracks_GT_Matched` dropped by the same proportion as the total (1570/4138=37.9% → 1486/3918=37.9%) — the fix merged fragmented noise-tracks together without changing the real signal-to-noise ratio, which is the honest reading of a flat match-rate, not a false positive.
- **True monocular baseline added** (`Step_2_3_2_YOLO_Monocular_Depth.ipynb`, `Step_3_4_Camera_Mono_Tracker.ipynb`): the existing "Camera" row (Step 2.3.1/3.3) is not actually camera-only — it borrows depth from LiDAR (median depth of LiDAR points falling inside each YOLO box), so it can't answer "how good is a camera alone, with no other sensor." Step 2.3.2 estimates depth from each YOLO box using the classic similar-triangles relationship (`depth = assumed_real_height_m * fy / pixel_height`, per-class height table, e.g. person 1.7m, car 1.5m, bus 3.4m — the one unavoidable scale assumption of a single 2D image), un-projects the box center at that depth back into 3D using the camera's own intrinsics, then lifts it to the global frame with the same `point_to_global()` utility Step 1.1/2.3.1/3.1/3.2 already share. Step 3.4 duplicates Step 3.3's `ClassAwareGlobalTracker` unchanged except for input directory and track-id prefix (`cammono_`), tracking these monocular-only detections the same way. Result (`camera_mono` row in `evaluation_metrics.csv`): MAE 3.75, RMSE 7.07, Good_pct 42.2 — meaningfully worse than the LiDAR-assisted `camera` row (MAE 2.86) but better than radar (5.53), which is a reasonable way to quantify exactly how much LiDAR depth-assistance is worth to the camera pipeline. Known limitation, not fixed: the per-class height table is a fixed average, so any real object's deviation from it (a child vs. an adult, a hatchback vs. an SUV) becomes a directly proportional depth error, and a partially truncated/occluded box's foreshortened pixel height reads as "further away," overestimating depth — this is the standard tradeoff of apparent-size monocular depth, not something this notebook attempts to correct.

**Fusion still doesn't beat the best individual sensor, but each fix above has closed the gap in the expected direction — verified on a clean, single, freshly-cleared run of every stage.** Progression of fused metrics across the three fixes above (`output/step_6/evaluation_metrics.csv`):

| Fix stage | Fused MAE | Fused RMSE | Fused Good_pct |
|---|---|---|---|
| Raw per-frame weighted-average merge (original) | 4.05 | 8.32 | 44.8 |
| + sensor-aware UKF measurement noise | 3.84 | 8.12 | 46.0 |
| + state-level fusion (this section) | **3.64** | **7.82** | **49.3** |

| fused | 3.63 | 7.79 | 49.5 |

With the Step 3.1 adaptive gate also applied: lidar MAE 3.54/RMSE 7.41/Good_pct 50.2, fused MAE 3.82/RMSE 8.11/Good_pct 49.6 — see the track-fragmentation section for why this tradeoff (less fragmentation, slightly worse per-point accuracy) is expected and how to improve on it. With the per-sensor R fix in Step 4's smoothing also applied, using measured (not assumed) camera/camera-mono variance (current on-disk state): fused MAE 3.81/RMSE 8.12/Good_pct 50.1, camera MAE 2.85/RMSE 5.85/Good_pct 52.6, camera_mono MAE 3.73/RMSE 6.98/Good_pct 42.3 — see the "R mis-tuning check" follow-up below for the two-pass story (assumed weights alone didn't help; measured weights for camera/camera-mono did, modestly).

Camera (LiDAR-assisted) remains the best individual sensor, with LiDAR close behind; fused has closed most of the gap to LiDAR but still trails both. The true monocular baseline sits between LiDAR and radar — worse than every LiDAR-assisted result, confirming that a meaningful share of the "camera" row's accuracy comes from borrowed LiDAR depth, not the camera detections themselves. Diagnosed cause: even with proper temporal smoothing per sensor, the fused pool is still dominated by single-sensor pass-through volume (~62% LiDAR-only, ~19% radar-only, only ~13% of points actually combine 2+ sensors) — no amount of filtering quality can make a radar-only frame (the worst individual sensor, MAE 5.53) as accurate as LiDAR's own, and averaging it in still drags the pool down. **Takeaway: state-level fusion is a genuine improvement over per-frame raw-position averaging, but the remaining gap is about sensor-pool composition, not filter quality** — a further improvement would need to selectively trust/exclude single-sensor segments (e.g. down-weighting or dropping radar-only points) rather than more UKF tuning.

## Track fragmentation investigation: methodology and findings

`fused` has 3918-4138 tracks (depending on which fix above is applied) against only ~695 real ground-truth instances (person/bicycle/car/motorcycle/bus/truck) across the 404 samples — a ~6x fragmentation ratio. This section documents how that number was actually chased down, including a methodology mistake caught mid-investigation and corrected, because the *process* here matters as much as the final fix: several plausible-sounding hypotheses were tested directly against the code and data and ruled out, rather than assumed.

**Step 1 — the `FusedTracker` continuation fix (documented above) closed one real mechanism.** Tracing one real pedestrian's ground-truth position against `fused_tracks_all.csv` found it mapped to 10 different fused IDs across a 41-frame lifetime, including two tracks literally coexisting for the same object at frames 90–93. That directly confirmed a bad-prediction-causes-duplicate-track mechanism in `FusedTracker`, fixed by switching its association prediction to the already-smoothed per-sensor velocity. Re-tracing the same pedestrian afterward: 10 IDs → 4, with no more overlapping duplicates. But aggregate `N_Tracks_Total` only dropped 5.3% (4138→3918) against a 60% reduction on the traced object — arithmetic that says most of the remaining excess isn't this same mechanism.

**Step 2 — tested and refuted "cross-sensor detections never merge on first contact."** Hypothesis: two sensors seeing the same new object in the same frame might spawn two separate single-sensor fused tracks that never merge. Tested directly: found 17 real car instances first-seen by both LiDAR and camera in the exact same frame, and checked what `fused_tracks_all.csv` shows for each at that frame. Result: **14/17 (82%) merged into one `camera+lidar` fused entry from frame one; 0/17 showed the hypothesized split.** This ruled out the initial cross-sensor merge gate as the dominant contributor — it works correctly in the large majority of cases tested.

**Step 3 — reframed toward per-sensor (LiDAR) fragmentation, and caught a real methodology mistake mid-investigation.** LiDAR alone already produces 3134 tracks for ~695 real objects (4.5x fragmentation) *before* Step 4 ever runs, and ~62% of all fused points are LiDAR-only pass-through — so LiDAR's own tracker looked like the likely dominant source. First attempt: traced a heavily-fragmented car (17 distinct nearest-LiDAR-track-IDs across 41 GT frames) purely by GT-position proximity. But checking one candidate segment (`track_43048abd`, 7 continuous points, samples 305–311) found it had *also* been "matched" to two other track IDs during that same span — a giveaway that position-proximity matching in a dense multi-lane scene can attribute a *different, nearby* real car's detection to the same GT box. **This confound was caught by inspecting the data, not assumed away** — a naive fragmentation count from this method would have been wrong in an unknown direction.

**Step 4 — corrected methodology: the tracker's own decision log, plus an independent shape signal.** Two changes fixed the confound: (1) reproduced `GlobalFrameTracker`'s exact algorithm in an instrumented script that logs *why* each track ends — eviction (missed-frame count exceeded `MAX_MISSED_FRAMES`), rejected-valid-match (an active track had a real detection within its gate, but Hungarian assigned it elsewhere), or no-candidate (genuinely nothing nearby) — verified faithful by an exact match to Step 3.1's own printed total (4799 tracks created, both places); (2) cross-checked each candidate segment's cluster shape (`num_points`, `extent` from `lidar_clusters.json`) for consistency, since two different real cars are very unlikely to share near-identical point counts and bounding-box dimensions across the same frames — this is exactly the check that would have caught the `track_43048abd` mismatch immediately (its `num_points` was ~100 vs. ~4500 for the genuine car segments). Applying both: 3 of the 17 candidates were confirmed noise (14-34 points vs. ~4500), and of the remaining 13 shape-consistent segments, **zero showed a rejected-valid-match event** — meaning during every eviction-driven break, no detection at all fell within the gate of that track's prediction, not that a competitor stole it.

**Finding: neither original sub-hypothesis (occlusion-gap vs. DBSCAN cluster instability) was quite right.** The 13 real segments have near-identical shape throughout (ruling out cluster instability) and their time windows tile almost continuously with virtually no true visibility gaps (ruling out occlusion — a shape-matching cluster reappears every 1-4 frames). The actual mechanism: each new track's velocity estimate comes from just its own last 2 points, and for this object's motion (fast and/or non-constant between 0.5s keyframes), that estimate is imprecise enough that the *predicted* position drifts past the fixed `ASSOC_DIST_THRESHOLD=3.0m` gate even though the real, continuously-visible, shape-consistent object never actually left view. This is a fixed-spatial-gate-vs-motion-uncertainty mismatch — the same reason production trackers use Mahalanobis/covariance-scaled gating instead of a flat Euclidean cutoff, re-derived here from evidence rather than assumed.

**Fix: adaptive (speed-scaled) association gate** (`Step_3_1_LiDAR_Fusion.ipynb`, `GlobalFrameTracker`): `gate = ASSOC_DIST_THRESHOLD + gate_speed_factor * speed * dt_since_last_seen` (`gate_speed_factor=0.5`), replacing the flat `ASSOC_DIST_THRESHOLD` check — a fast-moving track gets a wider net, a stationary one keeps the original 3.0m. Effect on the traced car: real (shape-confirmed) fragment count dropped from 13 to 6 segments (54%). Aggregate: total tracks created 4799→4301 (−10.4%), saved tracks (length≥2) 3134→2838 (−9.4%); downstream fused tracks 3918→3876.

**Honest tradeoff, not a clean win — reported as such.** LiDAR's own per-point accuracy got slightly *worse*, not better: MAE 3.29→3.54, RMSE 6.99→7.41, Good_pct 51.4→50.2 (fused similarly: MAE 3.63→3.82, RMSE 7.79→8.11). This is consistent with a pre-existing diagnostic already in `Step_3_1_LiDAR_Fusion.ipynb` showing the underlying 2-point velocity estimate is noise-dominated on this data (moves the prediction *closer* to the next real detection only 30.5% of the time). Widening the gate based on that same noisy speed estimate reduces fragmentation but also lets in a few incorrect associations it previously would have correctly rejected. **This is why the recommended next step is fixing the velocity estimate's noise (e.g. reusing the per-track UKF/CTRV smoothing already built for Step 4/5, rather than a 2-point finite difference) before tuning the gate further** — a wider gate on a bad estimate is a partial fix, not a complete one. Noted here as the natural follow-up, not implemented as of this investigation.

### Follow-up: R mis-tuning check, and the dilution anomaly resolved

Two further checks were run on the fused-accuracy gap (fused still trailing LiDAR/camera individually), following the same "verify against real data before changing anything" discipline as above.

**R was genuinely mis-tuned in one place, fixed in two passes.** `Step_4_Fusion.ipynb`'s per-sensor UKF smoothing (`smooth_track_states()`, which runs *before* any cross-sensor merge) used one fixed `R = np.diag([0.5, 0.5])` for LiDAR, radar, and camera alike, while Step 5's own per-dataset UKF already derived sensor-specific `R` from `SENSOR_TRUST_WEIGHT`. `SENSOR_TRUST_WEIGHT` was moved to `config.py` as a single shared source (Step 4's smoothing, Step 4's merge weighting, and Step 5's UKF all import it now, instead of three independent copies that could silently drift apart — the same failure class this pipeline already hit twice with radar's `dyn_prop`/velocity fields and the `["points"]` unwrap).

*Pass 1 — propagate the existing assumed weights, unchanged (lidar 44, radar 4, camera 1.0).* A controlled Kalman-gain comparison (same predicted state/covariance, only R varied) confirmed the fix behaves as intended: LiDAR's gain went 0.864→0.993 (trusts new measurements far more), camera's 0.864→0.760 (trusts them less). But fused MAE/RMSE moved slightly the *wrong* direction: 3.82→3.84 / 8.11→8.18 (Good_pct 49.6→49.8). Before assuming the fix itself was the problem, camera's assumed σ≈1.0m was checked for staleness (git history: both it and Step 2.3.1's LiDAR-depth-borrowing landed in the same initial commit, so it isn't outdated) and measured directly against ground truth: median 1.487m — *higher* than assumed, no case for lowering it at that point.

*Pass 2 — actually measure the variance, per-sensor, with a methodology check first.* Matched-track position vs. `sample_annotation` ground truth, MAD-based robust sigma (insensitive to a small fraction of mismatches). Camera: measured var 0.81 (94.8% inlier rate — trustworthy, well-formed tracks). Camera-mono: measured var 1.70 (95.0% inlier — also trustworthy; wasn't even in `SENSOR_TRUST_WEIGHT` before, silently defaulting to camera's trust level via a fallback and understating its real, worse noise). **LiDAR and radar could not be measured this way and were left at their assumed values (0.0225, 0.25)** — their much higher track fragmentation (4.1x/2.4x vs. camera's near-1x) means enough short tracks lock onto the *wrong* nearby vehicle in dense traffic that only ~86% of matched points are real inliers, not the >97% a robust estimator needs; even the *median* came out ~2.0m, physically impossible for LiDAR, proving this isn't a small-tail-outlier problem robustness could fix. Using that measurement would have made LiDAR/radar *less* trusted than the existing assumption, contradicting known sensor physics — a genuinely separate finding in its own right (fragmentation doesn't just hurt accuracy, it actively corrupts the ability to calibrate the pipeline that would fix it), not a failure of this fix.

Updated `SENSOR_TRUST_WEIGHT = {"lidar": 44.0, "radar": 4.0, "camera": 1.23, "camera_mono": 0.59}` (weights — `R = 1/weight` downstream, so camera's R became 0.81 and camera-mono's 1.70, verified numerically via the same Kalman-gain check using the real `config.py` values, not a hand-recomputation). One claimed "reciprocal inversion bug" was raised and checked directly against the code and a live numeric run — `R_camera` computed out to 0.813 and `R_camera_mono` to 1.695, both matching their measured variances almost exactly, confirming no inversion; camera-mono correctly ends up *less* trusted than camera (lower weight), not more. **Result: fused MAE 3.84→3.81, RMSE 8.18→8.12, Good_pct 49.8→50.1** — a small but genuine improvement, now that the correction is measurement-based rather than guessed, and confirmed not to be a formula error.

**The "long tracks are worst" dilution anomaly is real but was overstated by outliers, confirmed via per-track breakdown, and survived both R passes unchanged.** Bucketing fused's matched TTC points by track length (short <5 pts, medium 5-19, long 20+) showed medium best (MAE 3.04-3.17 across all three R settings tried) and long *worst* (5.33-5.96) — the opposite of what simple "young unconverged tracks drag the average down" dilution would predict. Breaking the long tracks down individually: median per-track MAE (~6) is close to the bucket average, but the *mean* (~12-13) is dragged up hugely by 6 tracks with only 1-4 matched points each and individual errors of 24-48s — these are long tracks (20+ total frames) that only briefly, sparsely locked onto ground truth, and that handful of isolated bad matches dominates the point-weighted bucket average. A robust check confirms it: **median point-error by bucket is consistently short≈1.2, medium≈0.8, long≈1.2** across all three R settings — under a statistic outliers can't dominate, "long is worst" mostly disappears; medium remains best but long is comparable to short, not catastrophic. The anomaly survived both the flat-weight R fix and the measured-variance R fix unchanged in shape, confirming it's fully independent of R-tuning — a small number of long tracks with sparse bad ground-truth locks, not a systematic long-track degradation or an R symptom.

### Verified correct (no bug found) — three checks worth recording so they aren't re-litigated

- **`centroid_to_global()` runs before tracking, not after.** Step 3.1's main loop builds `detections_global` via `centroid_to_global(...)` for every cluster, then passes that already-global list into `tracker.update()` — confirmed by reading the cell directly. Centroids are never in raw sensor-local frame (~1.8-2m above ground) when the tracker sees them.
- **Scene-boundary tracker resets are verified on real data, not just present in code.** Beyond `GlobalFrameTracker` checking `scene_name` on every update (documented above), Step 3.1's own `assert len(cross_scene_associations) == 0` runs against the real 404-sample/10-scene dataset on every execution and has passed every single run in this project's history — a violation would crash the notebook, which would have been visible.
- **TTC's sign convention for radar is correct, and the specific failure mode described doesn't structurally exist.** Radar's raw Doppler `relative_speed`/`vx`/`vy` fields are parsed and stored (Step 1.2/2.2) but never consumed by Step 5's TTC computation — grep-confirmed zero references. Radar tracks are plain `(sample_id, timestamp, [x,y,z])` position tuples, same as LiDAR; TTC velocity always comes from position deltas (UKF or finite-difference), never a raw sensor-reported speed with its own sign convention. Traced one real closing radar object (`track_035fae91`) through the actual formula: `closing_speed` is correctly positive (6.94→6.92→5.01 m/s) while distance shrinks (31.72→28.32→23.65m), giving sensible finite TTC (4.57s→4.09s→4.72s); once the object's own motion changed and it was no longer closing, `closing_speed` correctly went negative (-0.80) and `ttc` correctly became `inf` rather than a nonsensical negative or inverted value.

## Second audit round: fusion-specific fixes (radar velocity, camera double-counting, track confirmation)

A second audit pass, prompted by an external review of the fusion design, worked through a list of candidate root causes for fusion underperforming its best individual sensor. Each was checked against the actual code/data before being accepted or rejected, and each accepted fix was measured end-to-end (Steps 3→4→5→6 re-run) rather than assumed to help. Baseline going into this round: fused MAE 3.81 (camera_mono not yet in the fusion mix, radar velocity unused, no track confirmation).

- **Fusion was double-counting LiDAR.** The fused set was combining `lidar` with the LiDAR-assisted `camera` (Step 2.3.1, whose depth *is* a LiDAR point) — a "camera+lidar" merge was partly LiDAR agreeing with a copy of itself, not two independent views. Fixed by pointing Step 4's `CAMERA_TRACKS_DIR` at `camera_mono` (Step 3.4, genuinely independent monocular depth) instead — confirmed directly from `fused_tracks_all.csv`'s `sensors` column that `camera` (LiDAR-assisted) now never appears in the fused set at all, only `lidar`/`radar`/`camera_mono` combinations.
- **Radar's own Doppler velocity was parsed and stored back in Step 2.2 but never used anywhere** — every filter (Step 4's per-sensor smoothing, Step 5's per-dataset UKF) measured position only, for every sensor including radar. Fixed: `src/geometry.py` gained `vector_to_global()` (rotates a velocity vector — no translation, since a velocity has no position to translate); Step 3.2 now carries radar's rotated `(vx, vy)` alongside position (`[x,y,z,vx,vy]` instead of `[x,y,z]`); both Step 4's per-sensor smoothing and Step 5's standalone radar UKF now feed it in as a genuine second measurement channel (`ukf_update()` generalized to accept a measurement function, defaulting to the original position-only behavior for lidar/camera/camera_mono). Effect: **radar's own standalone MAE dropped from 5.53 to 3.80** (a 31% reduction, and more GT-matched pairs too, 678→801) — the single biggest single-sensor improvement in this round. New `RADAR_VELOCITY_NOISE_VAR = 1.0` (assumed, not measured, documented as such) in `config.py`.
- **Position and velocity were merged using the same trust weight, when they measure different things.** `SENSOR_TRUST_WEIGHT` is a position weight; reusing it for velocity assumes a sensor's velocity accuracy always tracks its position accuracy, which is false for radar (direct Doppler velocity, indirect position) — the opposite of lidar/camera_mono (velocity entirely derived from differencing their own position over time). Added `SENSOR_VELOCITY_TRUST_WEIGHT` (back-of-envelope-derived from each sensor's own position noise propagated through a 2-point difference at this pipeline's 2Hz cadence for lidar/camera_mono, and from radar's own `RADAR_VELOCITY_NOISE_VAR` directly) and split `merge_frame_observations()`'s single weighted average into two — one for position, one for velocity. Non-obvious finding, stated plainly rather than assumed away: **LiDAR's own *derived* velocity (var ≈0.18 (m/s)²) comes out more trusted than radar's *direct* Doppler measurement (var 1.0) at this sample rate** — LiDAR's position is precise enough that differencing it still beats an imperfect direct measurement. This is why the fused number barely moved from this specific change (multi-sensor-merged MAE 2.93→2.81) even though it's correctly implemented: in a lidar+radar merge, LiDAR rightly continues to dominate the velocity blend.
- **Reference-point mismatch between sensors, checked and refuted as the cause of the low multi-sensor merge rate.** Hypothesis: LiDAR/radar/camera report slightly different points on the same real object (centroid vs. strongest reflector vs. box-based estimate), and if that gap were large, no amount of merge-threshold tuning could fix it. Measured directly using ground truth to confirm "same real object" (avoiding circularity from using the merge threshold itself to decide that): median cross-sensor offset for a *confirmed-same* real object is under 1.3m for every sensor pair (lidar-radar 0.96m, lidar-camera_mono 0.83m, radar-camera_mono 1.23m), and only 5-7% of pairs exceed the 2.5m merge gate. **Refuted as the main cause.** Follow-up check found the real explanation: of 18,538 real GT object-instances checked across the dataset, 63.1% were detected by no sensor at all, 22.9% by exactly one sensor type, and only 14.1% by two or more sensor types simultaneously — a hard ceiling on how much multi-sensor fusion could ever happen, set by sensor field-of-view/detection-rate overlap, not by matching-distance tuning. The pipeline's actual multi-sensor merge rate (~25% of matched pairs) is already close to this ceiling.
- **Merge-distance threshold tuning, tried and reverted.** `INTRA_FRAME_MERGE_THRESH`'s sweep (already present in Step 4 as an unread experiment, Cell 11) showed raising it 2.5m→3.5m would lift the multi-sensor merge fraction 24.6%→29.3% with zero further gain past 3.5m (4.0m: also 14.3%). Tried it, measured end-to-end: fused MAE got *worse* (4.01→4.18), and — tellingly — both the newly-merged and the already-merged groups got worse together, consistent with the reference-point-offset explanation above (a wider gate catches more of both correct and incorrect merges roughly proportionally). Reverted to 2.5m; documented as tried-and-rejected directly in Step 4's own Cell 2 so it isn't re-attempted blind.
- **Timing offset between sensors, measured and left as a known, accepted limitation.** Every detection in a sample is stamped with one shared `timestamp_us`, but sensors don't fire at the same instant. Measured across all 404 samples via the real per-`sample_data` timestamps: LiDAR's offset is always exactly 0ms (it turns out `timestamp_us` *is* LiDAR's own capture time by nuScenes convention), camera's median offset is -25ms (up to 48ms), radar's is usually 0ms with a tail up to 35ms. At realistic speeds this is sub-meter position error (~0.14-0.7m) — real, and for camera specifically comparable to its own assumed measurement noise, but small against the pipeline's multi-meter overall error. Not fixed: doing so properly means threading each detection's own real timestamp through nearly every stage (Steps 1, 3, 4, 5, 6 all currently assume one shared clock per sample) — a large, invasive change for a sub-meter gain. (The separate async "v2" rebuild already solves this correctly from first principles, for exactly this reason.)
- **Track confirmation (M-of-N) added to all three trackers** (`GlobalFrameTracker` in Step 3.1/3.2, `FusedTracker` in Step 4): a brand-new (1-hit) track previously got the same `max_missed` eviction tolerance as an established one, letting a one-off noisy detection sit active and compete in Hungarian assignment for up to `max_missed` frames before being dropped — long enough to potentially intercept a detection meant for a different, genuinely separate object. An unconfirmed track (`hits < min_hits_to_confirm=2`) now gets a much shorter `tentative_max_missed=0` tolerance instead: it must be re-matched at the very next opportunity or is dropped immediately. Does not change which tracks get *saved* (`save_tracks()`/Step 4's Cell 7 already only wrote tracks with 2+ points; `hits` and point-count are the same number in this design) — only how long an unconfirmed one can linger and interfere with others first. **Measured, mixed result, kept anyway by deliberate choice:** LiDAR/radar saved-track counts dropped sharply (LiDAR 2756→2354, radar 1693→1293) as intended, but LiDAR's and radar's own MAE both got somewhat *worse* (3.54→3.79, 3.80→4.30) rather than better — most likely because a genuinely real but intermittently-detected object can now get fragmented into more, shorter pieces if it isn't re-seen on the literal next attempt, instead of surviving a brief natural gap. Fused MAE improved marginally (3.96, from 4.02). Kept as-is on the reasoning that it correctly solves the stated problem (no more one-off noise instantly becoming a lingering, competing track) and is an honestly-documented tradeoff, not a hidden regression — not because it was a clean accuracy win.

- **Fabricated single-detection velocity, checked and found already structurally impossible.** Concern: a track built from just one detection was silently given zero velocity in `smooth_track_states()`, which could then dilute a merge with a genuinely-established sensor as if it were real data. Implemented a proper fix (flagging fabricated velocity so the merge excludes it) — but verified directly that every saved track file (lidar/radar/camera_mono) has a minimum length of 2, because Step 3's own trackers already discard any track seen only once *before* it ever reaches Step 4. The fix is correct and harmless but currently inert; kept as a defensive safeguard in case that upstream guarantee ever changes. (This flag mechanism was later subsumed into the covariance-based merge below — an infinite velocity variance now produces the same zero-weight effect through one general rule instead of a special-cased flag.)
- **Filter noise assumptions, sanity-checked via NIS (Normalized Innovation Squared) for the first time.** Computed NIS (how surprised the filter should have been by each update vs. how surprised it actually was) against every real saved lidar/radar track. Finding: the *median* NIS is far *below* the theoretically expected value (lidar 0.09 vs. expected ~2; radar 1.14 vs. expected ~4) — the filter is typically *more cautious than necessary* — but the *mean* is dragged far above expectation (3.84, 5.12) by a ~9% tail of huge surprises, almost certainly the same mis-association problem already documented elsewhere (a detection matched to the wrong real object), not a general noise-miscalibration problem. Conclusion: broad Q/R retuning would not address the actual issue; the tail is an association-quality problem, not a noise-model problem.
- **New-track initial velocity uncertainty was one guessed constant (5.0) for every sensor**, regardless of that sensor's own known position accuracy or the specific track's own first-gap timing. Measured against honest error propagation (`Var(v) = 2*Var(position)/dt²`, using values already established elsewhere in this file): the flat 5.0 was ~28x too *small* for camera_mono's real first-guess noise (~14 (m/s)²) — falsely confident — and ~28x too *large* for LiDAR's (~0.18) — needlessly slow to trust very good early data. Fixed in both Step 4's smoothing and Step 5's standalone UKF to compute this per-sensor, per-track value from variables already in scope (no new constant needed). **Measured, mixed result:** LiDAR unchanged, but radar/camera/camera_mono's own MAE all moved slightly *worse* (camera_mono 3.73→3.83) and fused moved from 3.96 to 4.05. Likely cause: being honestly uncertain at the start means converging more slowly, and short-lived tracks (common for camera_mono) don't always survive long enough to cash in that slower-but-more-correct convergence — the old, overconfident guess sometimes produced a closer-looking answer for short tracks purely by chance. Kept anyway, same reasoning as track confirmation: it fixes a real conceptual inconsistency rather than optimizing this one dataset's score.
- **Fixed per-sensor merge weights replaced with genuine per-instant, per-track covariance-based fusion** — the most substantial architectural change in this round. Previously, `merge_frame_observations()` looked up one constant weight per sensor NAME (`SENSOR_TRUST_WEIGHT`/`SENSOR_VELOCITY_TRUST_WEIGHT`); it had no way to tell a track's own current confidence apart from its sensor's generic reputation. `smooth_track_states()` now returns each point's own live position variance (read directly from its own filter's covariance) and velocity variance (propagated from the filter's `[speed, heading]` covariance via a standard Jacobian linearization, since Cartesian velocity is a nonlinear function of that state) — the merge weights each contribution by `1/variance` at that exact instant instead of a fixed per-sensor number. This is the textbook-correct way to combine multiple uncertain estimates, and it let the earlier "fabricated velocity" flag be retired entirely (an infinite variance now produces the same zero-weight effect through the same general mechanism, one fewer special case). **Measured result: essentially flat** (fused MAE 4.05→4.08). Consistent with the NIS finding above — the real bottleneck is association correctness, not weighting precision, so a more sophisticated weighting scheme had little room to help. Kept regardless of the flat result: unlike the merge-threshold experiment (a pure tuning knob, reverted), this is a genuine correctness improvement with no other purpose it's trading away.

**The pattern across this whole round, worth stating plainly:** of all the fixes attempted, exactly one produced a large, unambiguous improvement — radar's own velocity, standalone MAE 5.53→3.80 — because it added genuinely new information the system never had before. Every other fix in this round (merge threshold, track confirmation, initial-variance realism, covariance-based weighting) was a real, defensible correctness improvement that moved the aggregate MAE by less than a few percent, in either direction. The honest reading: for this dataset and pipeline, the ceiling on fusion accuracy is set by *what information exists and whether it's attached to the right object* (sensor coverage overlap, association correctness), not by *how precisely* already-available information gets weighted or filtered once you have it.

## Verdict, noise floor, and per-change ablation (does fusion actually win, and which of the 11 changes did what)

The second audit round above bundled 11 changes into one commit (`3c529eb`), which made it impossible to credit or blame any one of them individually, and never stated plainly whether the end result actually beats the best single sensor. Both gaps are closed here by (1) measuring the run-to-run noise floor directly, and (2) reconstructing the round change-by-change from the pre-round baseline (`6b820f9`) by checking out that commit, replaying each change's code in isolation via the same edit scripts originally used to write it, and re-running Steps 3→6 after every step — with the final replayed step cross-checked against the real committed output as a fidelity check (it reproduced every number exactly, including `n_matched_pairs=2290 = 714+1576`, confirming the reconstruction is faithful).

**Noise floor: exactly zero.** The entire pipeline (DBSCAN, Hungarian assignment, the UKF/CTRV math) is deterministic. ## Deep research: the real reason single-sensor passthrough is worse inside fusion than the sensor alone

The composition breakdown above (multi-sensor merged MAE 2.65 vs. single-sensor passthrough MAE 4.73, and passthrough is 68.8% of all matched fused pairs) already pointed at *where* the problem lives, but not *why* — a single-sensor passthrough point should, in principle, be no worse than that same sensor evaluated standalone, since it isn't combined with anything else. It measurably is worse for all three sensors (lidar 4.39 vs. 3.79 standalone, radar 5.96 vs. 4.32, camera_mono 4.65 vs. 3.83), and this section documents tracking that gap down to its actual mechanism, ruling out several plausible causes along the way with direct code-level tests rather than assumption.

**Ruled out: a math or hyperparameter difference between Step 4's and Step 5's UKF.** These are documented elsewhere in this file as duplicated-but-not-unified, which is the obvious first suspect. Diffed `merwe_sigma_points`, `ctrv_process`, `ukf_predict`, `ukf_update` between the two notebooks byte-for-byte: identical except docstrings. Not the cause.

**Ruled out: a smoothing bug — the two pipelines produce bit-identical output for the same input.** Executed Step 4's real `smooth_track_states()` and Step 5's real `run_ttc_pipeline()` directly (not re-implemented — the actual cell source, exec'd) on the same 2354 native LiDAR tracks loaded from `output/step_3/lidar/track_*.json`. Result: **100% numerically identical** `(x, y, vx, vy)` at every one of 11,975 compared points (diff < 1e-9). Given the same raw track, Step 4's per-sensor smoothing computes exactly what Step 5's standalone pipeline would. This also rules out track segmentation feeding the smoother differently — both loaders (`load_lidar_or_radar_tracks()` in Step 4, `load_single_sensor_tracks()` in Step 5) read the identical `track_*.json` files the identical way.

**Found: `FusedTracker` re-derives track identity from scratch on already-tracked, already-smoothed data, and fragments it.** Since the smoothed values are proven identical, any accuracy difference has to come from what happens *after* smoothing — and `merge_frame_observations()` → `FusedTracker` is a second, independent re-tracking pass (its own Hungarian assignment, its own gate, its own M-of-N confirmation) applied on top of positions that the *native* per-sensor tracker (Step 3.1/3.2/3.4) already tracked and already confirmed once. It has no notion of "this point already belongs to a continuous, established native track" — it treats every frame's smoothed observation as a fresh detection needing its own confirmation from zero.

Measured directly, with a low-ambiguity methodology chosen specifically to avoid a false-positive risk in dense traffic (two different real objects can sit within tens of centimeters of each other, so a naive nearest-position join across the two pipelines produces false matches — an earlier looser attempt at this comparison hit exactly that trap and was discarded): recomputed fresh per-track smoothing for all 2354 native LiDAR tracks, then matched each of its points against `fused_tracks_all.csv`'s lidar-only rows only when there was **exactly one candidate within 1cm** at that sample (i.e., provably the same point, not a coincidentally-nearby different object — only 1 ambiguous case out of thousands). Of native tracks with 3+ such unambiguously-identified points, **64.8% (149/230) end up split across 2 or more different `fused_id`s** — some severely: one clean, 19-frame native track (gaps no larger than 3 frames, well inside the native tracker's own tolerance, which is exactly why it survived as one track natively) had its 5 identifiable lidar-only points land in **5 separate fused-level tracks** — every single frame refragmented into its own island. This is not occlusion or real ambiguity; it is redundant re-confirmation discarding work the native tracker already did.

**Why this inflates MAE even though the underlying positions are perfect: the GT-matching methodology (`match_predictions_to_ground_truth()`, above) locks a track's identity once, at its first frame, and reuses that lock for every subsequent point in the track.** More fragments per real object means more independent "first-frame lock" attempts across the same underlying trajectory. Average lock quality is *not* worse in the fragmented case (median first-lock distance is 1.79m in both the native and re-tracked populations) — but more independent attempts at a fixed per-attempt risk means more total exposure to a bad lock, corrupting a larger share of otherwise-perfectly-accurate points. This is a pure evaluation-methodology-meets-architecture interaction: the position data was never wrong; the fragmentation manufactures more chances for the lock-once methodology to anchor a good trajectory to the wrong ground-truth object.

**Quantified impact.** Reconstructing fused's overall MAE from the per-sensor passthrough numbers (lidar-only n=829 MAE=4.39, radar-only n=258 MAE=5.96, camera_mono-only n=489 MAE=4.65, multi-sensor-merged n=714 MAE=2.65) reproduces the real committed fused MAE of 4.08 exactly, confirming the breakdown is internally consistent with production. Substituting each sensor's own *standalone* MAE for its passthrough MAE (i.e., the hypothetical where fusion's re-tracking caused zero extra fragmentation penalty) gives a reconstructed fused MAE of **3.50** — which would beat both LiDAR (3.79) and camera_mono (3.83), leaving only camera (2.87) ahead. That's a ~14% reduction from today's 4.08, and it is the largest single lever identified across either audit round — bigger than any individual fix in the second audit round, including radar velocity's 31% standalone win, because single-sensor passthrough is 68.8% of all fused matched pairs versus radar's much smaller share of the pool.

**Fixed, and measured end-to-end — see the next section for the result.** The straightforward fix is architectural: when `merge_frame_observations()` produces a single-sensor (unmerged) observation for a frame, `FusedTracker` inherits that observation's own `source_track_id` as its association key instead of re-solving assignment via its own gate/Hungarian/confirmation logic from scratch — collapsing single-sensor passthrough fragmentation back down toward whatever the native tracker already achieves, and only falling back to `FusedTracker`'s own from-scratch association logic for genuinely multi-sensor frames (which have no single native `source_track_id` to inherit). This was a bigger structural change than anything in the second audit round (it changes `FusedTracker`'s core association logic, not just a weight or a threshold), so it was measured the same way every other fix in this file is — end-to-end, not assumed to help.

## Fix: FusedTracker identity inheritance, implemented and measured

Implemented the fix proposed above (`Step_4_Fusion.ipynb`, `FusedTracker`). Each merged observation already carries the `(sensor, source_track_id)` pair(s) that produced it (from `merge_frame_observations()`'s own `source_track_ids` field) — previously computed but never used by `FusedTracker`. Added `self.identity_to_track`, a map from every `(sensor, source_track_id)` ever seen to whichever fused track last claimed it, persisting across the *whole* run rather than being cleared per frame or on eviction. On each frame, a new identity-inheritance pass runs before the existing Hungarian assignment: for every observation whose recorded native tag(s) point unambiguously at exactly one fused track, that track is matched directly — reviving it from `finished_tracks` if it had been evicted, since the native tracker's own record is proof the object never actually left view, regardless of what a frame-gap counter says. An observation whose tags point at *two different* existing fused tracks (a genuine merge-of-two-previously-separate-tracks event) is deliberately left to the unchanged Hungarian path below, since there's no single correct identity to inherit there. A shared `_predict()`/`_apply_match()` pair of helper methods keeps both paths — identity-inherited and Hungarian-matched — behaviorally identical once a match is decided (same velocity-extrapolated prediction, same `BLEND_ALPHA` blending), so the only actual change is *which* mechanism decides a match, not what happens afterward.

Measured end-to-end (Steps 4→5→6 re-run; lidar/radar/camera/camera_mono are untouched by this change and confirmed byte-identical — 2354/1293/1131/953 tracks, same MAE — verifying the change is correctly isolated to fusion-level tracking):

|---|---|---|---|
| Fused MAE | 4.08 | 3.90 | −4.4% |
| Fused RMSE | 8.39 | 7.82 | −6.8% |
| Fused tracks (`N_Tracks_Total`) | 3079 | 2987 | −3.0% (less fragmentation) |

**Real, but partial — the fix closes roughly a third of the diagnosed gap, not all of it.** The deep-research section's theoretical ceiling (passthrough recovering to each sensor's own standalone accuracy) put fused MAE at ≈3.50; the measured result is 3.90 — a genuine, non-trivial 4.4% improvement, but well short of that ceiling. This is expected, not a discrepancy: identity inheritance can only fire once a native id has appeared before and can therefore be looked up — a track's very first appearance, and any genuinely ambiguous multi-sensor-composition-change frame, still goes through the unchanged Hungarian path with its own M-of-N confirmation. The fix eliminates *needless* re-fragmentation of already-proven continuations; it doesn't eliminate every source of fragmentation.

**Honest verdict: a real win, but it doesn't flip the headline result.** Fused (3.90) still trails LiDAR (3.79, a 2.9% gap, down from 7.6%) and camera (2.87, a 36% gap, down from 42%), and is now essentially tied with camera_mono (3.83) rather than clearly worse. This is the largest single accuracy gain from any *structural* (non-tuning) change to the fusion architecture attempted so far — bigger than any single change in the second audit round except radar velocity's standalone win — but on its own it does not make fusion competitive with the best individual sensor. The remaining gap is consistent with the other, separately-documented ceilings this fix doesn't touch: the sensor-coverage-overlap ceiling (only 14.1% of real objects seen by 2+ sensors) and the NIS-tail association-quality issue.

**The small increase in the multi-sensor-merged bucket's MAE (2.65→2.83) is reported here rather than glossed over.** With less needless fragmentation, a few points that previously landed in short, separately-locked passthrough segments now stay attached to a longer continuous track whose GT lock was established earlier, possibly under a different sensor composition — a small, plausible side effect of the same mechanism driving the passthrough improvement, not a separate bug. It's a proportionally larger percentage move (+6.8%) on a much smaller, already-good number, and it's outweighed by the passthrough bucket's larger absolute improvement (which is 75.6% of all matched pairs, versus the merged bucket's 24.4%) — net effect on the aggregate is still a clear improvement, as the fused MAE figure shows.

## Further tuning and analysis: a second bug found and fixed, fragmentation fully eliminated, and the real shape of what's left

Asked directly why fusion was still underperforming after the identity-inheritance fix, re-ran the same low-ambiguity fragmentation test from the deep-research section against the *new* (post-fix) output to see how much it actually helped, rather than assuming the job was done.

**A second bug, found by tracing a specific still-fragmented track frame by frame.** The re-measured fragmentation rate had dropped from 64.8% to 14.3% — real progress, but not zero. Picked the worst remaining case (a clean, 32-frame stationary object, gaps never exceeding 3 frames) and traced it through a full re-execution of the actual pipeline functions with instrumentation at every frame. Found: when a real object's two sensors momentarily drift apart by just over `INTRA_FRAME_MERGE_THRESH` for a single frame — the same object, still detected by both, but no longer close enough for `merge_frame_observations()` to combine them into one observation — `merge_frame_observations()` correctly emits two separate observations that frame, and *both* carry a tag proving they belong to the same existing fused track. The identity-inheritance pass could only award the match to whichever observation it processed first; the second, entitled to the exact same track, found it already claimed, fell through to Hungarian, discovered the one correct candidate had just been excluded from the pool by the first observation's claim, and spawned a brand-new phantom track instead of recognizing it was redundant. Fixed by dropping (not Hungarian-matching) an observation whose unambiguous identity tag is already claimed by another observation in the same frame — the track already got a good update from the other sensor this frame, so the second one is discarded rather than allowed to fork a duplicate.

Measured end-to-end: fused MAE 3.90→3.91 (flat — within noise of the prior fix, not a regression), RMSE 7.82→7.87 (a small, real uptick), matched pairs 2388→2322. **Re-running the fragmentation test after this fix: 0.0% (0/109) of clean multi-point native LiDAR tracks are split across 2+ fused_ids — full elimination**, down from 64.8% before either fix and 14.3% after the first one alone. Kept despite the flat-to-slightly-worse aggregate number, on the same reasoning as several fixes in the second audit round: it corrects a real, demonstrated mechanism (a phantom-track-spawning bug), not a tuning knob, and the fragmentation metric — the thing actually being fixed — moved cleanly to its logical floor of zero.

**The important finding: with fragmentation now fully eliminated, the remaining single-sensor-passthrough gap is not a tracking bug — it's revealed to be a real, different-in-kind effect.** Re-ran the per-sensor-combination breakdown (from the deep-research section) on the fragmentation-free output:

|---|---|---|---|
| lidar-only | 3.97 | 3.79 | +0.18 (was +0.60 before either fix) |

LiDAR's gap closed by 70% and is now close to parity — exactly what "eliminate needless refragmentation" should do when the underlying data was already good. Radar and camera_mono's gaps barely moved, even though their own fragmentation rates are *also* independently confirmed at 0% (re-ran the same low-ambiguity test against the radar-only bucket: 276 native tracks checked, 0 split). Since neither the smoothing math (proven identical earlier) nor the track segmentation (now proven 1:1 with the native tracker) can explain it, this gap is something else: **objects that ever get corroborated by a second sensor are tracked far longer than objects that never do.** Measured directly: fused tracks containing at least one genuine multi-sensor-merged frame average 9.38 frames of total length; fused tracks that are pure-radar for their entire life average only 3.68 — 2.5x shorter. This means single-sensor "passthrough" isn't a random sample of each sensor's own track population; it's weighted toward the objects that were *never* picked up by anything else, which independently correlates with shorter, more marginal, more error-prone detections (consistent with radar's known false-positive/clutter tendency and the previously-documented sensor-coverage-overlap ceiling). This is a genuine population-composition effect, not an architecture defect — there's no tracking bug left to fix here; the passthrough bucket is inherently harder than the standalone pool it's compared against, in a way further tuning of the fusion tracker cannot correct.

**One further tuning knob tried and reverted, in the same spirit as the second audit round's honestly-negative attempts.** With identity inheritance now handling every already-established continuation, the only tracks left exposed to `tentative_max_missed=0`'s harsh 1-strike eviction are genuinely brand-new ones. Measured end-to-end: fused MAE 3.91→3.91 (no change), RMSE 7.87→7.86, matched pairs 2322→2338 — a small handful of extra tracks survive, with zero net effect on accuracy. Reverted to the default; documented in Step 4's own Cell 6 instantiation so it isn't re-tried blind.

## The merge-of-two-tracks ambiguous case: tried, measured worse, reverted

The two prior fixes deliberately left one case alone: an observation whose contributing native ids point at 2+ *different* existing fused tracks (identity inheritance's own `len(candidates) != 1` fallthrough). On the reasoning that `merge_frame_observations()`'s union-find had already decided these detections are close enough to be the same real object this frame — the identical criterion the rest of the pipeline uses for "same object" at the single-detection level — it seemed reasonable that the two previously-separate fused tracks they grew into were always the same real object, just not yet corroborated by both sensors.

Implemented a real merge: `_merge_tracks()` picked the more-established of the two candidates (by hit count) as the survivor, retired the other into `finished_tracks`, and re-pointed every historical `(sensor, source_track_id)` tag that had ever pointed at the retired track onto the survivor — so any future reappearance of either track's native ids would correctly continue the one real object.

**Measured end-to-end, this made things worse, not better: fused MAE 3.91→3.93, RMSE 7.87→7.99, matched pairs 2322→2173.** Instrumented the actual run to understand why before deciding whether to keep it: 420 merge events fired, and of the 432 "losing" tracks absorbed into a survivor, **227 (52%) already had 3+ hits of their own independently-established history — some as many as 28.** That's direct, measured evidence the underlying assumption doesn't transfer from single-detection merging to whole-track merging: `merge_frame_observations()`'s per-frame criterion is applied fresh every frame and only risks one bad frame of averaging if it's wrong (already known and accepted, at a 5-7% error rate, from the earlier reference-point-mismatch investigation), but permanently fusing two *entire track histories* on the strength of one coincidental frame of proximity is a much bigger bet — and with real, multi-object driving scenes (two pedestrians walking near each other, a car passing close to a motorcycle), that bet loses often enough to net negative. A track with 28 independent hits is almost certainly a genuine, distinct, well-tracked real object; merging it into another track's identity because they were briefly 2.5m apart corrupts both trajectories going forward, not just the one frame.

Reverted `_merge_tracks()` entirely; the ambiguous case falls through to the pre-existing Hungarian competition, exactly as it did after the first identity-inheritance fix. This is a smaller, well-contained mechanism (one frame's worth of mis-assignment risk, not a permanent identity corruption), and empirically the better choice of the two. Documented directly in Step 4's own Cell 6 so this specific fix isn't re-attempted blind. Current state is unchanged from the previous section's table (fused MAE 3.91) — this was a negative result, not a further improvement.

## Why sensor fusion performs lower than individual sensors — consolidated summary

The three sections above are the full investigation trail; this section is the one-stop answer, for anyone who wants the conclusion without the methodology. Current state (`output/step_6/evaluation_metrics.csv`): fused MAE **3.91** vs. LiDAR **3.79** (a 3.2% gap) and camera **2.87** (36%) — fusion still loses to the two best individual sensors, though the gap has narrowed considerably from where the second audit round left it (7.6% and 42%).

**1. The composition effect (the largest factor).** `output/step_4/fused_tracks_all.csv` is 87.4% single-sensor points and only 12.6% genuine multi-sensor merges. Scored separately, merged points have MAE 2.74 — beating every individual sensor — while single-sensor "passthrough" points score 4.43. Fusion works exactly as intended whenever it actually happens; the aggregate number is dragged down because passthrough is 75.5% of all matched pairs and merges are only 24.5%.

**2. The sensor coverage ceiling (why merges are rare) — confirmed partly self-imposed, not pure physics.** Measured directly against ground truth: of 18,538 real object-instances, 63.1% were seen by zero sensors, 22.9% by exactly one, and only 14.1% by two or more simultaneously (this session's own re-measurement, on the same methodology, found a similar shape: 60.9%/21.5%/17.7%). Isolated and tested each candidate self-imposed cause separately (see "Radar declutter filter relaxed" further down): radar's moving-only declutter was confirmed to be excluding real, accurate, GT-annotated stationary objects, not just clutter — relaxing it raised 2+-sensor coverage from 17.7% to 25.2% and was adopted as a permanent fix. YOLO's confidence threshold was tested the same way and found *not* to have the same property (relaxing it raised coverage but also hurt accuracy) — reverted, not adopted.

**3. Two real tracking bugs (found, fixed, measured).** `FusedTracker` was re-deriving track identity from scratch every frame instead of inheriting a contributing sensor's already-established native track id, and had a "de-merge" conflict that spawned phantom duplicate tracks when one real object's two sensors drifted apart for a single frame. Fixing both eliminated needless fragmentation of clean native tracks from 64.8% → 14.3% → **0.0%**, and moved fused MAE from 4.08 → 3.90 → 3.91.

**4. What's left is a real population effect, not a bug.** With fragmentation fully eliminated, the remaining passthrough gap (LiDAR 3.97 vs. 3.79 standalone, radar 5.83 vs. 4.32, camera_mono 4.46 vs. 3.83) persists because single-sensor-only objects are structurally different: tracks ever corroborated by a second sensor average 9.38 frames of life; tracks that stay single-sensor their whole life average only 3.68 — 2.5x shorter. Passthrough is inherently weighted toward the harder, more marginal detections nothing else ever picked up.

**5. A further fix was tried and made things worse (honest negative result).** Merging ambiguous multi-candidate track identities (two previously-separate tracks proven, by one frame of proximity, to be the same object) regressed MAE 3.91 → 3.93: 52% of the "losing" tracks already had 3+ independently-established hits, meaning the assumption too often merged two genuinely different real objects. Reverted.

**Bottom line (updated after the radar-filter fix below):** fusion underperforms because most of what it outputs isn't actually fused — it's single-sensor pass-through dominated by the harder-to-detect subset of each sensor's own population, bounded by real sensor coverage limits. Part of that "hard ceiling" turned out to be self-imposed rather than pure sensor physics: radar's own moving-only declutter filter was silently discarding real, easy-to-track stationary objects (mostly parked cars) alongside genuine noise. Fixing it was the single largest accuracy win in this whole investigation — see "Radar declutter filter relaxed" below for the full measurement — and pushed fused ahead of LiDAR for the first time. The YOLO confidence threshold was checked the same way and found *not* to have the same property. What's left to tune in `FusedTracker`'s own association logic is now genuinely exhausted; any further gain would need better upstream single-sensor detection quality or merge-weighting that distrusts historically-uncorroborated observations.

## Bug found: fused output was not actually deterministic — fixed, true baseline is MAE 3.94 not 3.91

While investigating whether the coverage ceiling (Section 4 above) is self-imposed by the pipeline's own detection filters, re-running the unchanged baseline code to get a clean comparison point surfaced something that hadn't been caught before: **the fused output was not reproducible run to run**, contradicting the noise-floor finding earlier in this file (which was established before the identity-inheritance and de-merge fixes existed).

**Symptom.** Re-running Steps 3.2/3.4→4→5→6 on identical code with no input changes gave fused MAE 3.85, then 3.90, then 3.94, then 3.90 again across successive attempts — every individual sensor (LiDAR, radar, camera, camera_mono) stayed perfectly stable at their documented values every single time; only the *fused* number moved.

**Root cause.** `Step_4_Fusion.ipynb`'s loaders (`load_lidar_or_radar_tracks()`, `load_camera_tracks()`) iterate `track_dir.glob("track_*.json")`. Track filenames are fresh random `uuid4` hex on every run (`save_tracks()`'s own convention, documented elsewhere in this file), and `Path.glob()` over a directory that was just `shutil.rmtree()`'d and recreated does not guarantee any particular enumeration order run to run. This never mattered before: the old `FusedTracker` used pure Hungarian assignment, which finds the *globally optimal* assignment from the cost matrix alone, invariant to the order its inputs are listed in. But this round's identity-inheritance and de-merge fixes (see above) both have a tie-breaking rule that is explicitly "whichever observation is processed first" — and with an unordered `glob()`, "first" silently meant something different every run.

**First fix attempt was insufficient.** Sorting `glob()`'s results alphabetically by filename fixed determinism *for a fixed set of already-written files* (two re-runs of Step 4 alone, reusing the same Step 3 output, became stable) — but failed a real end-to-end test: regenerating Step 3.2/3.4 fresh (new random filenames) still gave a different fused number each time (3.85/3.90/3.94 across three genuinely independent full pipeline runs), because alphabetically sorting *random* filenames just reshuffles the real tracks' relative order differently every time their names are re-randomized.

**Actual fix: sort by content, not by filename.** Each loader now collects all tracks first, then sorts by `(first_point_timestamp, first_point_x, first_point_y)` — a stable, content-derived key — before assigning tags and populating `tracks_by_id`/`observations_by_sample`. Verified genuinely fixed: two fully independent runs (fresh Step 3.2/3.4 execution, brand-new random UUIDs each time, all the way through Step 6) now produce byte-identical `evaluation_metrics.csv` output.

**This changes the documented baseline.** The **3.91** fused MAE reported in every section above was itself just one non-deterministic outcome of this bug, not a stable ground truth. With determinism restored, the actual, reproducible current-state fused MAE is **3.94** (RMSE 8.00, 2859 tracks, 2336 matched pairs) — every individual sensor's numbers are unaffected (LiDAR 3.79, radar 4.32, camera 2.87, camera_mono 3.83, all unchanged). This is a small upward revision (3.91→3.94, +0.8%), not a reversal of any conclusion above — the composition effect, coverage ceiling, and population-composition findings all still hold — but it is the correct number to use as the baseline for any future comparison, including the radar/YOLO coverage-ceiling experiments below.

## Radar declutter filter relaxed: stationary objects were being excluded, not just clutter (adopted)

Following up on the coverage-ceiling caveat raised above — "part of this ceiling is the pipeline's own conservative choices... not yet separately isolated" — tested the hypothesis directly by relaxing radar's `MOVING_DYN_PROPS` filter (`Step_2_2_Radar_Processing.ipynb`) to include genuine stationary-object `dyn_prop` states (1 stationary, 3 stationary candidate, 7 stopped) alongside the existing moving/oncoming/crossing-moving states, and measuring the effect end-to-end rather than assuming it would help.

**Verified safe before adopting, not just measured once:**
- **Isolated the real mechanism from noise inflation.** A targeted relaxation (adding only the 3 genuine-stationary-object states) reproduced ~99% of the effect of relaxing *every* `dyn_prop` value (radar coverage 41.6% vs. 42.4%, 2+-sensor overlap 25.2% vs. 25.5%) — confirming the gain is real stationary-object recovery, not coincidental matches from a flood of ambiguous/noise states.
- **Checked for double-counting.** Of GT instances newly covered by both LiDAR and radar, 77.6% properly merge into one genuine `lidar+radar` fused entry; only 2.7% end up as separate, non-merged duplicates.
- **Verified determinism** (after fixing the ordering bug documented above): measured twice independently, with Step 3.2 regenerated fresh (brand-new random track-ID UUIDs) both times — byte-identical results both times.
- **Ran a companion experiment on YOLO's confidence threshold** (0.35→0.15) to check whether the *same* pattern (a detection-count filter incidentally excluding real objects) applied elsewhere. It didn't in the same way: coverage rose similarly (camera_mono 21.0%→28.4%) but accuracy got slightly *worse* (camera_mono MAE 3.83→3.89, fused 3.94→3.97) — unlike radar's stationary objects (inherently easy, zero velocity-estimation uncertainty), low-confidence YOLO boxes are genuinely noisier, not just previously-excluded-but-accurate. **Not adopted; reverted.**

## RANSAC non-determinism confirmed and fixed — LiDAR's true reproducible baseline is MAE 3.77, not 3.57 or 3.79

The open question above was resolved by direct testing rather than left as a plausible guess.

**Confirmed the hypothesis first, before writing any fix.** Re-ran `Step_2_1_LiDAR_Processing.ipynb` on unchanged code/input and diffed `output/step_2/lidar_summary.csv` against a pre-run snapshot: `sample_0000`'s ground-point count alone moved 14863→10671 (a 28% swing), with every one of the first 5 samples differing meaningfully. This is decisively larger than any plausible floating-point/ordering noise — `segment_plane()`'s RANSAC genuinely resamples differently every call, and `o3d.geometry.PointCloud.segment_plane()`'s own signature confirms it takes no seed argument.

**Fix: Open3D's global seed hook.** Open3D 0.19.0 (the version pinned by `requirements.txt`) exposes `o3d.utility.random.seed(seed: int)`, a global RNG seed not mentioned on `segment_plane()`'s own docstring but confirmed by `dir(o3d.utility)` to exist and to control exactly this randomness. Verified in isolation before touching the notebook: (1) seeding before each of 3 repeated `segment_plane()` calls in one process gives identical inlier counts every time, while different seeds give different results — confirming the seed genuinely drives the behavior, not coincidence; (2) running the same seeded script as two **separate process launches** gives identical output — confirming the fix survives process boundaries, the actual requirement for two independent `nbconvert` executions to agree; (3) seeding **once** and then processing 5 different samples in sequence (matching the real pipeline's one-seed-call-then-loop structure) gives identical per-sample results across two separate process runs — confirming one seed call at the top is sufficient for the whole 404-sample loop, not just a single isolated call.

Applied: `Step_2_1_LiDAR_Processing.ipynb` Cell 4 now calls `o3d.utility.random.seed(LIDAR_RANSAC_SEED)` (`LIDAR_RANSAC_SEED = 42`) once, immediately after the imports and before the main per-sample loop begins.

**Verified end-to-end, twice over, at both the stage level and the full-pipeline level — not assumed from the isolated test alone:**
- Step 2.1 alone, run twice independently: `lidar_summary.csv` byte-identical both times.
- Steps 2.1→3.1→4→5→6, run twice independently (fresh random track-file UUIDs each time, same as every other determinism check in this file): `evaluation_metrics.csv` byte-identical both times.
- Step 7's full audit re-run clean afterward: 36 PASS, 0 FAIL, 7 OK, 1 WARN.

**Result: LiDAR's true, now-reproducible MAE is 3.77** (RMSE 7.85, 2327 tracks, 1907 matched pairs) — close to the originally-committed 3.79 (a 0.5% difference, well within the kind of small shift a fixed-but-different seed value would produce) and nowhere near the user's manual run's unseeded 3.57. This confirms the 3.57/2385 figures committed in the previous section were indeed a non-deterministic artifact of the unseeded RANSAC call, not a new stable number — they are superseded by this section, not averaged with it.

The small movement from that section's committed 3.52/3.79 to this section's 3.55/3.77 is attributable to the LiDAR RANSAC seed changing which exact points fall on which side of the ground-plane cut (a few points per sample reclassified, cascading into slightly different clusters and tracks) — expected from fixing a previously-undefined random draw to a specific value, not a sign of a remaining bug. **The general lesson, worth remembering for any future randomized-algorithm call in this codebase: a library call that "just happens to be deterministic enough in practice" should never be assumed reproducible without fixing its seed explicitly and testing across process boundaries — same discipline as the earlier `FusedTracker` glob-ordering bug, different library, same root cause (unexamined call into a randomized routine).**

## Step 8: Bird's-Eye-View fusion video

A terminal visualization stage, added on request to make the fusion result visually inspectable rather than only readable as a CSV of metrics. For each of the 404 samples, renders a combined frame: a left panel showing an ego-centered, heading-up **Bird's-Eye View** with every sensor's detections for that frame (LiDAR cluster centroids, post-declutter radar points, true-monocular `camera_mono` detections across all 6 cameras) plus the **fused** tracks active that frame, each labeled with its fused TTC and color-coded by urgency (red < 3s, orange < 6s, yellow < 10s, green otherwise, gray = no finite TTC yet); and a right panel showing the real `CAM_FRONT` image for that sample with the fused TTC projected directly onto it.

**Camera-panel TTC overlay reuses the existing projection chain, capped and boxed on request.** Each fused track's global `(x, y, z)` is projected into the camera's image plane via `src/geometry.py`'s `global_points_to_camera()` — the same math Step 2.3.1/3.1/3.2 already use, no new geometry. First version drew a point marker per visible track; with ~15-20 fused tracks often visible in one frame, distant objects near the image's vanishing point (e.g. a row of parked cars receding down a street) clustered into unreadable overlapping labels. Fixed two ways, both on request: (1) capped to `NEAREST_N_CAMERA=6` objects, selected by the same ego-`distance` Step 5 already computes for TTC, not just "first N in the data"; (2) replaced the point marker with an actual 2D bounding box, derived by projecting a generic axis-aligned 3D box (`BOX_HALF_EXTENT_M=1.2`, `BOX_HEIGHT_M=1.8`, centered on the track's position) to pixel space and taking the bounding rect of whichever corners land in frame — not class-aware (fusion doesn't carry a class through to this stage), so every object gets the same generic footprint/height rather than a per-class size, but the box still scales correctly with perspective since it's a real 3D projection, not a fixed pixel size.

**Scope decision: one MP4 per scene (10 videos), not one combined file.** nuScenes v1.0-mini's 404 samples are actually 10 separate continuous driving clips (scenes) concatenated in the index — the same fact that motivated the scene-boundary-isolation fix in Steps 3.1/3.2/3.3. A single combined video would have 9 visible jump-cuts at the scene boundaries; one video per scene instead matches how the data was actually recorded, consistent with "the video as it was in the input."

**fps is measured per scene, not assumed.** Each video's frame rate is derived from that scene's own real `timestamp_us` deltas (median inter-sample interval), not a hardcoded constant — this reproduces the original recording's actual temporal cadence rather than guessing. All 10 scenes measured out to the dataset's standard 2.0 Hz keyframe rate, confirming there's no per-scene timing irregularity worth accounting for separately.

**BEV orientation reuses existing math, not new conventions.** The ego-local, heading-up transform is just `src/geometry.py`'s `transform_matrix(ego_pose["translation"], ego_pose["rotation"], inverse=True)` — the same global-to-ego inversion already used elsewhere in the pipeline, applied here for visualization instead of tracking. No new coordinate convention was introduced.

Outputs: `output/step_8/videos/<scene_name>.mp4` (10 files) and `output/step_8/bev_video_summary.csv` (per-scene frame count/fps). This stage reads only already-committed outputs (Steps 0–5) and writes nothing any other stage consumes — it's correctly excluded from Step 7's audit scope (which only walks Steps 0–6).
