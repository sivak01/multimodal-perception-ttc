# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A multi-sensor (camera + radar + LiDAR) fusion research pipeline built on the **nuScenes v1.0-mini** dataset. It reconstructs, from raw sensor logs, per-object tracks in a global frame, fuses them across sensors, and computes Time-To-Collision (TTC) estimates for evaluation against ground-truth annotations. There is no application code — the entire pipeline is a sequence of numbered Jupyter notebooks, each a self-contained pipeline stage that reads the previous stage's output from disk and writes its own.

There is no test suite, linter, or build system — correctness is checked via the notebooks themselves (see Step 7 below) and by re-running stages.

## Running the pipeline

Notebooks must be run **in numeric order**, top to bottom, since each stage's outputs are the next stage's inputs (all paths flow through `config.py`, see below). There's no CLI entry point — open notebooks in Jupyter/VS Code and run all cells, or execute headlessly:

```bash
jupyter nbconvert --to notebook --execute --inplace "Step_0_Dataset_Preparation.ipynb"
```

Pipeline order:

| Stage | Notebook | Purpose |
|---|---|---|
| 0 | `Step_0_Dataset_Preparation.ipynb` | Indexes nuScenes samples; writes `samples_index.json`, the master index every downstream step reads |
| 1.1 | `Step_1_1_Camera_Preprocessing.ipynb` | Camera calibration/intrinsics per sample; imports `project_point_to_camera()` from `src/geometry.py` |
| 1.2 | `Step_1_2_Radar_Parsing.ipynb` | Parses raw radar point clouds per channel |
| 1.3 | `Step_1_3_LiDAR_Parsing.ipynb` | Parses raw LiDAR point clouds (N×7 arrays: point + derived fields) |
| 2.1 | `Step_2_1_LiDAR_Processing.ipynb` | Ground-plane removal (Open3D `segment_plane`) + DBSCAN clustering |
| 2.2 | `Step_2_2_Radar_Processing.ipynb` | Radar filtering (dynamic-property filter) + feature extraction (raw + ego-compensated velocity) |
| 2.3 | `Step_2_3_YOLOv5.ipynb` | YOLO 2D object detection on camera frames (uses `ultralytics`, weights in `yolov8n.pt`) |
| 2.3.1 | `Step_2_3_1_YOLO_Global_Projection.ipynb` | Lifts each 2D YOLO box to a 3D global-frame position by fusing with LiDAR |
| 2.3.2 | `Step_2_3_2_YOLO_Monocular_Depth.ipynb` | Lifts each 2D YOLO box to 3D using similar-triangles depth-from-height (no LiDAR) — a true monocular-only baseline; see below |
| 3.1 | `Step_3_1_LiDAR_Fusion.ipynb` | Multi-frame LiDAR tracking (nearest-neighbor / Hungarian assignment via `scipy.optimize.linear_sum_assignment`), global frame |
| 3.2 | `Step_3_2_Radar_Fusion.ipynb` | Multi-frame radar tracking, same family as 3.1; clusters multi-blip radar returns into one detection per object before tracking |
| 3.3 | `Step_3_3_Camera_Tracker.ipynb` | Multi-frame camera tracking (LiDAR-assisted depth), global 3D nearest-neighbor across all 6 cameras |
| 3.4 | `Step_3_4_Camera_Mono_Tracker.ipynb` | Same tracker design as 3.3, reading Step 2.3.2's monocular-only detections instead |
| 4 | `Step_4_Fusion.ipynb` | Fuses LiDAR/radar/camera tracks into unified tracks — runs its own per-sensor UKF/CTRV smoothing on each contributing sensor track first, then merges the smoothed states (state-level fusion; see below). Does not include the camera-mono baseline. |
| 5 | `Step_5_TTC.ipynb` | UKF + CTRV motion model → TTC estimate per track for LiDAR/radar/camera/camera-mono; the fused dataset already carries state-fused velocity from Step 4, so it skips straight to TTC instead of re-filtering |
| 6 | `Step_6_Visualization.ipynb` | Trend plots + evaluation metrics against nuScenes `sample_annotation` ground truth |
| 7 | `Step_7_Pipeline_Audit.ipynb` | Read-only audit: walks Steps 0–6 checking input/output counts and known-bug regressions at every stage; does not modify any output |
| — | `Validate_Step_2_3_1.ipynb` | Standalone validator for Step 2.3.1's 3D projections |

Each notebook's first markdown cell documents its own **Input / Outputs / Used by** table — read that cell before modifying a stage, since output schemas are contracts downstream notebooks depend on exactly (e.g. LiDAR/radar tracks are tuple-format, camera tracks are dict-format — Step 4 handles both explicitly).

## Architecture

**`config.py` is the single source of truth for all paths.** Every notebook starts by importing from it (e.g. `from config import STEP0_DIR, STEP1_DIR, ...`). It anchors `PROJECT_ROOT`/`BASE_DIR` to its own file location (not the Jupyter CWD), points `DATA_ROOT` at the nuScenes dataset, and derives one output subdirectory per stage (`STEP0_DIR` … `STEP6_DIR`) under `output/`. **Change dataset/output locations only in `config.py`** — never hardcode paths inside a notebook.

**`src/geometry.py`** holds the sensor-to-global and global-to-camera coordinate transform math (`transform_matrix`, `point_to_global`, `points_to_global`, `project_point_to_camera`, `global_points_to_camera`). This used to be copy-pasted independently into Steps 1.1, 2.3.1, 3.1, and 3.2; those notebooks now `from src.geometry import ...` instead. Step 2.3.2 (monocular depth baseline) also imports `point_to_global()` from here, to lift its similar-triangles depth estimate into the global frame the same way every other stage does. Step 3.1 imports `point_to_global` under the alias `centroid_to_global` to match its existing call sites. If you touch this file, all four notebooks are affected — re-run them to confirm. `GlobalFrameTracker` (Step 3.1 vs 3.2), `compute_ttc` (Step 5 vs Step 6), and now the UKF/CTRV core (`merwe_sigma_points`/`ctrv_process`/`ukf_predict`/`ukf_update`, Step 4 vs Step 5) are similarly duplicated but were *not* unified — their implementations have diverged enough (radar-specific tuning, ground-truth-specific lookups, Step 4's per-sensor-track smoothing vs Step 5's per-dataset TTC runner) that merging them needs a closer read than a mechanical extraction; treat that as a known follow-up, not an oversight. Verified by executing all four notebooks end-to-end (`python -m nbconvert --to notebook --execute ...` — note `python -m jupyter nbconvert` silently exits 1 with no output on at least one Windows setup seen in this repo's history; call `nbconvert` as a module directly instead); Step 3.1's per-run diagnostic numbers matched the pre-refactor baked-in output exactly.

**Step 3.1, Step 3.2, Step 3.3, and Step 4 used to not be idempotent — now fixed.** `save_tracks()` (all three trackers) writes `track_<uuid4>.json` with a fresh random id every run, and previously never cleared its output directory first, so re-running any of them without deleting that directory first accumulated duplicate track files on top of the previous run's (confirmed: re-running Step 3.1 once turned 4930 LiDAR track files into 9860). Each of the four notebooks' setup cells now `shutil.rmtree()`s its own output directory before recreating it, so a plain re-run always produces a clean single-run result — no manual deletion needed anymore.

**This already silently happened once, undetected, and contaminated a committed evaluation table.** The `evaluation_metrics.csv` "after" numbers referenced below (and the "fusion got worse" finding) were computed on top of Step 3 output that had accumulated across two runs without clearing: LiDAR's on-disk `8072` = `4930` stale pre-declutter-fix tracks + `3142` from the real post-fix run (confirmed exactly: `4930+3142=8072`, and `3142` matches the notebook's own committed cell output at commit `bac3e4e`); radar's on-disk `13760` was ~8x the real single-run count (~1698). Camera happened to only ever run once (`1131` on disk = `1131` in the committed cell output) so it's clean. This was only caught by chance while diagnosing an unrelated track-count change during the scene-boundary-isolation fix below — **treat every number in the "fusion got worse" table as unverified until Steps 4–6 are re-run on a freshly-cleared, single-run Step 3 output** (Step 3 was re-cleared and re-run clean as of that fix: LiDAR 3152, radar 1693, camera 1131 saved tracks).

Data flow is entirely file-based: each stage reads JSON/CSV/NPY files written by the prior stage under `output/step_N/...` and writes its own under `output/step_(N+1)/...`; there is no in-memory hand-off between notebooks. Key artifacts:
- `output/step_0/samples_index.json` — master sample index, read by nearly every later stage. Each entry: `sample_token`, `scene_token`, `scene_name`, `timestamp_us` (authoritative `sample['timestamp']`, not any one sensor's own capture time — see fix below), `prev_token`/`next_token` (`""` at scene start/end), `folder`, `sensors`.
- `output/step_1/lidar/<sample>/lidar_raw.npy` — per-point LiDAR array (N×7).
- `output/step_2/yolo_global/<sample>/<camera>.json` — YOLO detections lifted to 3D global coordinates (LiDAR-assisted depth).
- `output/step_2/yolo_mono/<sample>/<camera>.json` — YOLO detections lifted to 3D via similar-triangles depth-from-height (no LiDAR); see below.
- `output/step_3/{lidar,radar,camera,camera_mono}/track_<id>.json` — per-sensor multi-frame tracks in the global frame.
- `output/step_4/fused/track_<id>.json` and `fused_tracks_all.csv` — fused multi-sensor tracks; `x,y,z` and `vx,vy` are already state-level fused (see below), not raw positions.
- `output/step_5/ttc_{lidar,radar,camera,fused}.csv` — same schema across sensors, directly comparable.

`html/` holds rendered HTML exports of each notebook (for viewing without Jupyter) and is regenerated from the notebooks, not hand-edited. `archive/` and `Old Codes/` hold prior notebook revisions and an old zipped copy of the project kept for reference — do not treat them as current; the root-level `Step_*.ipynb` files are canonical. `assets/` holds a small set of result images copied from `output/` and committed for the README — it's curated by hand, not regenerated automatically, so re-copy into it manually after a pipeline run if you want the README images refreshed.

`output/`, `DATA SET/`, `html/`, `archive/`, and `Old Codes/` are gitignored (see `.gitignore`); `assets/` is intentionally not.

## Known data-quality fixes and their measured effect

These were identified by auditing pipeline behavior against actual code (not assumed), then verified by re-running the affected notebooks end-to-end:

- **Authoritative sample timestamp + scene metadata** (`Step_0_Dataset_Preparation.ipynb`): the master index's timestamp was `list(sensor_meta["sensor_channels"].values())[0]['timestamp']` — an arbitrary sensor's own capture time (whichever channel happened to be first in `sample['data']`'s dict order), off from the true sample timestamp by up to ~45ms. Now uses the authoritative `sample['timestamp']`, stored as `timestamp_us`. Also added `scene_token`/`scene_name`/`prev_token`/`next_token` per sample (needed by the scene-boundary-isolation fix below), a 12-channel presence check, and an `_source_channel` tag on `ego_pose.json` recording which sensor's pose was used. The `timestamp_us` rename was cascaded to every downstream reader (Steps 3.1, 3.2, 4, 5, 6) so nothing silently breaks on `KeyError: 'timestamp'`.
- **Radar declutter** (`Step_2_2_Radar_Processing.ipynb`): the `dyn_prop` filter only excluded value `7`; the nuScenes enum has several other "not really moving" values (`1` stationary, `3` stationary candidate, `4` unknown, `5` crossing stationary). Now keeps only `{0, 2, 6}` (moving/oncoming/crossing-moving — the devkit's own recommended set for "moving objects only"). Effect: ~158 → ~27.5 kept detections/sample.
- **Radar blip clustering** (`Step_3_2_Radar_Fusion.ipynb`): one real object produces 3–8 separate radar blips; there was no grouping step before tracking. DBSCAN (`RADAR_CLUSTER_EPS = 1.5m`, `min_samples=1`) now groups blips into one centroid per object before they reach `GlobalFrameTracker`.
- **LiDAR cluster shape filter** (`Step_2_1_LiDAR_Processing.ipynb`, optional/lowest-priority): discards DBSCAN clusters whose bounding box is implausible for a vehicle/pedestrian (`CLUSTER_MIN_HEIGHT_M`/`MAX_HEIGHT_M`/`MAX_HORIZONTAL_EXTENT_M`/`MAX_ASPECT_RATIO` in the cell) — filters out curbs, hedges, wall fragments. Effect: ~66.3 → ~44.0 clusters/sample. Also hardened: `skipped_samples` tracking (same pattern as Step 1.3) for missing `lidar_raw.npy`, and a strengthened completion assertion cross-checked against Step 1.3's own row count (`output/step_1/lidar_summary.csv`) instead of only checking `summary_rows` is non-empty. **`CLUSTER_MAX_HORIZONTAL_EXTENT_M=15.0` checked against a real worst case, not just assumed correct**: `sample_0023` has the most shape-discards of any sample (55). Of those, only 2 were rejected specifically for `too wide/long`, and neither looks like a real vehicle — one is 21.3m long with 13,255 points (more LiDAR returns than most entire scenes' non-ground clouds combined; almost certainly a DBSCAN-merged wall/building fragment, not a single object), the other is a near-square 16.1m×9.7m footprint at only 2.18m tall (real buses/trucks are long and *narrow*, ~2.5–3m wide, not this). The other 53 discards in that sample are all genuinely flat (`dz<0.4m` — road paint, curbs, debris). Conclusion: don't loosen this threshold based on this evidence — doing so would let implausible merged blobs back into the tracked-object pool, not recover missed buses/trucks. Separately, this same check surfaced a real but out-of-scope issue: even some *kept* clusters in this sample look like under-segmented multi-object blobs (e.g. a kept 12.4m×13.6m×3.6m cluster) — DBSCAN's `eps`/`min_samples` may be too permissive in dense scenes; flagged as a follow-up, not fixed here.
- **YOLO class/confidence filter** (`Step_2_3_YOLOv5.ipynb`): was `model.classes = None` (all 80 COCO classes) at `conf=0.25`. Now `model.classes = [0,1,2,3,5,7]` (person/bicycle/car/motorcycle/bus/truck only) at `conf=0.35`.
- **Fusion merge Bug A** (`Step_4_Fusion.ipynb`, `merge_frame_observations()`): nothing prevented two detections from the *same* sensor from being merged together (e.g. two real pedestrians seen only by LiDAR could get squashed into one). Fixed: the union edge now requires different sensors.
- **Fusion merge Bug B**: the old pass was greedy (single forward scan), not a real union-find, so a chain of 3+ pairwise-close detections split into multiple clusters instead of one. Fixed with a proper disjoint-set union — verified by unit test (3 collinear points, 2m apart, `merge_thresh=3` → now one cluster, not `{p0,p1}` + `{p2}`).
- **Fusion averaging weighted by sensor trust**: was a flat `np.mean` over merged positions, treating LiDAR/radar/camera as equally accurate. `SENSOR_TRUST_WEIGHT = {"lidar": 44, "radar": 4, "camera": 1}` (inverse-variance-style, from ~0.15m/~0.5m/~1.0m assumed position noise) now weights the merge — verified by unit test (LiDAR+radar 1m apart merges to 91.7% toward LiDAR, as the weight ratio implies).
- **Evaluation scorecard** (`Step_6_Visualization.ipynb`, `compute_evaluation_metrics()`): `n_tracks_matched`/`n_tracks_total` were computed and printed to console but never added to the returned dict, so they never reached `evaluation_metrics.csv` — now included as `N_Tracks_Total`/`N_Tracks_GT_Matched`. The console message *"tracks found a GT lock at their first frame"* was misleading — `match_predictions_to_ground_truth()` actually retries the lock attempt every frame until one succeeds, not only frame 1; message text corrected. Added a sanity check that warns if two sensors report suspiciously identical `n_matched_pairs`.
- **`src/geometry.py` hardening** (additive only — no existing math changed): `tests/test_geometry_projection.py` cross-validates `project_point_to_camera()` against nuScenes devkit's own independent `Box.translate/rotate` + `view_points()` chain on real ground-truth boxes across 5 samples/2 scenes/2 cameras, including a dedicated high-yaw-rate turn sample (179° between consecutive samples) — all pass at 0.0000px deviation. Added a non-fatal frame-contract warning to `global_points_to_camera()` for suspiciously local-looking input (mean `|xyz|` below a threshold); calibrated to 100m, not the naively-plausible 5m, since this dataset's real local LiDAR sweeps average ~10m mean magnitude (median ~6m) while its global frame sits around 1100–1250m — a 5m cutoff would never actually fire. Added `project_points_to_camera_batch()` (precomputes one combined 4×4 transform instead of rebuilding per point) as a batch-safe alternative to the scalar function for any future per-point-in-a-loop reuse; verified identical to the scalar function on 100 real points (0.0000px difference). Note: as of this fix, `src/geometry.py`'s projection functions are wired into Steps 1.1, 2.3.1, 3.1, and 3.2 only — `Step_4_Fusion.ipynb` does not import from it at all (grep-confirmed), despite Step 1.2's markdown once implying otherwise (now corrected there too).
- **Step 1.2 hardening** (`Step_1_2_Radar_Parsing.ipynb`): `samples_index` load moved into Cell 1 so the diagnostic cell (Cell 2) is truly optional/deletable without breaking the main parse loop (verified: deleting it and re-running produces identical output). Added a `failed_channels` aggregate tracker writing `parse_failures.json` (written even when empty). Corrected a false markdown claim that this notebook "reuses `project_point_to_camera()` from Step 1.1" — it never has; the per-point calibration it stores is for a downstream notebook to consume.
- **Scene-boundary isolation** (`Step_3_1_LiDAR_Fusion.ipynb`, `Step_3_2_Radar_Fusion.ipynb`, `Step_3_3_Camera_Tracker.ipynb`): all three trackers process every sample in one continuous loop with no notion of nuScenes scene boundaries (v1.0-mini has 10 scenes, i.e. 9 boundaries across the 404 samples), so nothing stopped a track from associating the last frame of one scene with the first frame of the next. Each tracker (`GlobalFrameTracker`, `ClassAwareGlobalTracker`) now takes a `scene_name` argument, and at a scene change force-finalizes every active track and starts a fresh, empty track table — no ID, motion state, or last-known-position carried across. Each also logs every accepted association as `(prev_sample_id, prev_scene, curr_sample_id, curr_scene)` and asserts zero cross-scene entries at the end of its run. Verified two ways (in-run assertion + an external scan of every saved track's sample_ids against `samples_index.json`'s `scene_name`): 0 cross-scene associations, 0 scene-spanning tracks, on all three sensors. Note this was already true *before* the fix too — at `ASSOC_DIST_THRESHOLD=3.0m` two different scenes are never spatially/temporally close enough to false-match — so this is a correctness/defense-in-depth fix, not one that was visibly corrupting prior results.
- **Step 3/4 non-idempotency fix** (`Step_3_1_LiDAR_Fusion.ipynb`, `Step_3_2_Radar_Fusion.ipynb`, `Step_3_3_Camera_Tracker.ipynb`, `Step_4_Fusion.ipynb`): each stage's setup cell now `shutil.rmtree()`s its own output directory before recreating it, so a re-run always produces a clean single-run result instead of accumulating duplicate `track_<uuid4>.json` files on top of the previous run's (see the non-idempotency note above — this fixes it rather than just documenting it).
- **`timestamp_us` cascade was incomplete** (`Step_5_TTC.ipynb`, `Step_6_Visualization.ipynb`): despite the Step 0 fix above claiming the `timestamp_us` rename was "cascaded to every downstream reader," both notebooks' own duplicated ego-position-lookup cells (`ego_pos_by_sample`, used to compute the ego vehicle's global position/velocity for TTC) still read the old `info["timestamp"]` key, which no longer exists on `samples_index.json` entries. Both crashed with `KeyError: 'timestamp'` on a clean re-run. Fixed by changing both to `info["timestamp_us"]` — a one-line change in each notebook's cell.
- **Sensor-aware UKF measurement noise** (`Step_5_TTC.ipynb`): the UKF's measurement noise `R` was a single fixed `np.diag([0.5, 0.5])` regardless of which sensor(s) produced a given fused point — and `fused_df` didn't even carry the `sensors` column into the TTC pipeline, so the filter had no way to know a frame came from noisy radar vs. precise LiDAR. Added `measurement_noise_for(sensors_field)`, deriving `R` from the same `SENSOR_TRUST_WEIGHT` values Step 4's merge already uses (combined variance of an inverse-variance-weighted merge is `1 / sum(weights)`), applied per-row inside the UKF loop. Effect on fused: MAE 4.05→3.84, RMSE 8.32→8.12, Good_pct 44.8→46.0. Single-sensor datasets barely moved, as expected (homogeneous source, only the absolute noise value changed).
- **State-level fusion, replacing per-frame raw-position averaging** (`Step_4_Fusion.ipynb`, `Step_5_TTC.ipynb`): previously, Step 4 merged raw single-frame positions across sensors (weighted average), and Step 5 then ran one UKF over that merged stream from scratch — so the filter had no track history and started blind every time sensor composition changed frame-to-frame (confirmed: 25.8% of fused tracks switch composition at least once). Step 4 now runs the same UKF/CTRV model independently and continuously on each contributing sensor's own track *before* any cross-sensor merge (new cell, `smooth_track_states()`), then `merge_frame_observations()` combines each sensor's already-smoothed `(x, y, vx, vy)` state — not raw positions — still trust-weighted by `SENSOR_TRUST_WEIGHT`. `fused_tracks_all.csv` now carries real `vx`/`vy` columns. Step 5's fused path (`run_ttc_pipeline_state_fused()`) no longer re-filters this stream at all — it computes TTC directly from the already-fused velocity, since re-running a from-scratch UKF on already-fused-and-smoothed data would just reintroduce the same blind-restart problem. Effect on fused: MAE 3.84→3.64, RMSE 8.12→7.82, Good_pct 46.0→49.3.
- **`FusedTracker` next-frame prediction used a noisier estimate than it had to** (`Step_4_Fusion.ipynb`): frame-to-frame association predicted a track's next position from a fresh 2-point finite-difference of its own last two raw positions, discarding the already-smoothed per-sensor UKF `vx`/`vy` each point carries (from the state-level fusion fix above). A bad prediction pushed the real next detection outside `FUSION_DIST_THRESHOLD=3.0m`, causing Hungarian to miss a valid association and spawn a duplicate track for an object that never left view — confirmed directly by tracing one real pedestrian (see the track-fragmentation investigation below): two fused tracks were found coexisting for the same object across frames 90–93, positions diverging to 4m+ apart. Fixed to prefer the point's own smoothed `vx`/`vy` for prediction, falling back to the old finite-difference only if a point ever lacks a smoothed velocity (defensive, not currently reachable — every point Step 4 produces already carries one). `dt_now` already used real timestamps, not nominal spacing, so no change was needed there. Effect: fused `N_Tracks_Total` 4138→3918 (−5.3%); the traced pedestrian's fragment count dropped 10→4 with no more overlapping duplicates. MAE/RMSE/Good_pct barely moved (3.64→3.63 / 7.82→7.79 / 49.3→49.5) — expected, since this fixes track *identity continuity*, not per-point position/velocity accuracy. `N_Tracks_GT_Matched` dropped by the same proportion as the total (1570/4138=37.9% → 1486/3918=37.9%) — the fix merged fragmented noise-tracks together without changing the real signal-to-noise ratio, which is the honest reading of a flat match-rate, not a false positive.
- **True monocular baseline added** (`Step_2_3_2_YOLO_Monocular_Depth.ipynb`, `Step_3_4_Camera_Mono_Tracker.ipynb`): the existing "Camera" row (Step 2.3.1/3.3) is not actually camera-only — it borrows depth from LiDAR (median depth of LiDAR points falling inside each YOLO box), so it can't answer "how good is a camera alone, with no other sensor." Step 2.3.2 estimates depth from each YOLO box using the classic similar-triangles relationship (`depth = assumed_real_height_m * fy / pixel_height`, per-class height table, e.g. person 1.7m, car 1.5m, bus 3.4m — the one unavoidable scale assumption of a single 2D image), un-projects the box center at that depth back into 3D using the camera's own intrinsics, then lifts it to the global frame with the same `point_to_global()` utility Step 1.1/2.3.1/3.1/3.2 already share. Step 3.4 duplicates Step 3.3's `ClassAwareGlobalTracker` unchanged except for input directory and track-id prefix (`cammono_`), tracking these monocular-only detections the same way. Result (`camera_mono` row in `evaluation_metrics.csv`): MAE 3.75, RMSE 7.07, Good_pct 42.2 — meaningfully worse than the LiDAR-assisted `camera` row (MAE 2.86) but better than radar (5.53), which is a reasonable way to quantify exactly how much LiDAR depth-assistance is worth to the camera pipeline. Known limitation, not fixed: the per-class height table is a fixed average, so any real object's deviation from it (a child vs. an adult, a hatchback vs. an SUV) becomes a directly proportional depth error, and a partially truncated/occluded box's foreshortened pixel height reads as "further away," overestimating depth — this is the standard tradeoff of apparent-size monocular depth, not something this notebook attempts to correct.

**Fusion still doesn't beat the best individual sensor, but each fix above has closed the gap in the expected direction — verified on a clean, single, freshly-cleared run of every stage.** Progression of fused metrics across the three fixes above (`output/step_6/evaluation_metrics.csv`):

With the per-sensor R fix in Step 4's smoothing also applied, using measured (not assumed) camera/camera-mono variance (current on-disk state): fused MAE 3.81/RMSE 8.12/Good_pct 50.1, camera MAE 2.85/RMSE 5.85/Good_pct 52.6, camera_mono MAE 3.73/RMSE 6.98/Good_pct 42.3 — see the "R mis-tuning check" follow-up below for the two-pass story (assumed weights alone didn't help; measured weights for camera/camera-mono did, modestly).

Camera (LiDAR-assisted) remains the best individual sensor, with LiDAR close behind; fused has closed most of the gap to LiDAR but still trails both. The true monocular baseline sits between LiDAR and radar — worse than every LiDAR-assisted result, confirming that a meaningful share of the "camera" row's accuracy comes from borrowed LiDAR depth, not the camera detections themselves. Diagnosed cause: even with proper temporal smoothing per sensor, the fused pool is still dominated by single-sensor pass-through volume (~62% LiDAR-only, ~19% radar-only, only ~13% of points actually combine 2+ sensors) — no amount of filtering quality can make a radar-only frame (the worst individual sensor, MAE 5.53) as accurate as LiDAR's own, and averaging it in still drags the pool down. **Takeaway: state-level fusion is a genuine improvement over per-frame raw-position averaging, but the remaining gap is about sensor-pool composition, not filter quality** — a further improvement would need to selectively trust/exclude single-sensor segments (e.g. down-weighting or dropping radar-only points) rather than more UKF tuning.

## Track fragmentation investigation: methodology and findings

`fused` has 3918-4138 tracks (depending on which fix above is applied) against only ~695 real ground-truth instances (person/bicycle/car/motorcycle/bus/truck) across the 404 samples — a ~6x fragmentation ratio. This section documents how that number was actually chased down, including a methodology mistake caught mid-investigation and corrected, because the *process* here matters as much as the final fix: several plausible-sounding hypotheses were tested directly against the code and data and ruled out, rather than assumed.

**Step 1 — the `FusedTracker` continuation fix (documented above) closed one real mechanism.** Tracing one real pedestrian's ground-truth position against `fused_tracks_all.csv` found it mapped to 10 different fused IDs across a 41-frame lifetime, including two tracks literally coexisting for the same object at frames 90–93. That directly confirmed a bad-prediction-causes-duplicate-track mechanism in `FusedTracker`, fixed by switching its association prediction to the already-smoothed per-sensor velocity. Re-tracing the same pedestrian afterward: 10 IDs → 4, with no more overlapping duplicates. But aggregate `N_Tracks_Total` only dropped 5.3% (4138→3918) against a 60% reduction on the traced object — arithmetic that says most of the remaining excess isn't this same mechanism.

**Step 2 — tested and refuted "cross-sensor detections never merge on first contact."** Hypothesis: two sensors seeing the same new object in the same frame might spawn two separate single-sensor fused tracks that never merge. Tested directly: found 17 real car instances first-seen by both LiDAR and camera in the exact same frame, and checked what `fused_tracks_all.csv` shows for each at that frame. Result: **14/17 (82%) merged into one `camera+lidar` fused entry from frame one; 0/17 showed the hypothesized split.** This ruled out the initial cross-sensor merge gate as the dominant contributor — it works correctly in the large majority of cases tested.

**Step 3 — reframed toward per-sensor (LiDAR) fragmentation, and caught a real methodology mistake mid-investigation.** LiDAR alone already produces 3134 tracks for ~695 real objects (4.5x fragmentation) *before* Step 4 ever runs, and ~62% of all fused points are LiDAR-only pass-through — so LiDAR's own tracker looked like the likely dominant source. First attempt: traced a heavily-fragmented car (17 distinct nearest-LiDAR-track-IDs across 41 GT frames) purely by GT-position proximity. But checking one candidate segment (`track_43048abd`, 7 continuous points, samples 305–311) found it had *also* been "matched" to two other track IDs during that same span — a giveaway that position-proximity matching in a dense multi-lane scene can attribute a *different, nearby* real car's detection to the same GT box. **This confound was caught by inspecting the data, not assumed away** — a naive fragmentation count from this method would have been wrong in an unknown direction.

**Step 4 — corrected methodology: the tracker's own decision log, plus an independent shape signal.** Two changes fixed the confound: (1) reproduced `GlobalFrameTracker`'s exact algorithm in an instrumented script that logs *why* each track ends — eviction (missed-frame count exceeded `MAX_MISSED_FRAMES`), rejected-valid-match (an active track had a real detection within its gate, but Hungarian assigned it elsewhere), or no-candidate (genuinely nothing nearby) — verified faithful by an exact match to Step 3.1's own printed total (4799 tracks created, both places); (2) cross-checked each candidate segment's cluster shape (`num_points`, `extent` from `lidar_clusters.json`) for consistency, since two different real cars are very unlikely to share near-identical point counts and bounding-box dimensions across the same frames — this is exactly the check that would have caught the `track_43048abd` mismatch immediately (its `num_points` was ~100 vs. ~4500 for the genuine car segments). Applying both: 3 of the 17 candidates were confirmed noise (14-34 points vs. ~4500), and of the remaining 13 shape-consistent segments, **zero showed a rejected-valid-match event** — meaning during every eviction-driven break, no detection at all fell within the gate of that track's prediction, not that a competitor stole it.

**Finding: neither original sub-hypothesis (occlusion-gap vs. DBSCAN cluster instability) was quite right.** The 13 real segments have near-identical shape throughout (ruling out cluster instability) and their time windows tile almost continuously with virtually no true visibility gaps (ruling out occlusion — a shape-matching cluster reappears every 1-4 frames). The actual mechanism: each new track's velocity estimate comes from just its own last 2 points, and for this object's motion (fast and/or non-constant between 0.5s keyframes), that estimate is imprecise enough that the *predicted* position drifts past the fixed `ASSOC_DIST_THRESHOLD=3.0m` gate even though the real, continuously-visible, shape-consistent object never actually left view. This is a fixed-spatial-gate-vs-motion-uncertainty mismatch — the same reason production trackers use Mahalanobis/covariance-scaled gating instead of a flat Euclidean cutoff, re-derived here from evidence rather than assumed.

**Fix: adaptive (speed-scaled) association gate** (`Step_3_1_LiDAR_Fusion.ipynb`, `GlobalFrameTracker`): `gate = ASSOC_DIST_THRESHOLD + gate_speed_factor * speed * dt_since_last_seen` (`gate_speed_factor=0.5`), replacing the flat `ASSOC_DIST_THRESHOLD` check — a fast-moving track gets a wider net, a stationary one keeps the original 3.0m. Effect on the traced car: real (shape-confirmed) fragment count dropped from 13 to 6 segments (54%). Aggregate: total tracks created 4799→4301 (−10.4%), saved tracks (length≥2) 3134→2838 (−9.4%); downstream fused tracks 3918→3876.

**Honest tradeoff, not a clean win — reported as such.** LiDAR's own per-point accuracy got slightly *worse*, not better: MAE 3.29→3.54, RMSE 6.99→7.41, Good_pct 51.4→50.2 (fused similarly: MAE 3.63→3.82, RMSE 7.79→8.11). This is consistent with a pre-existing diagnostic already in `Step_3_1_LiDAR_Fusion.ipynb` showing the underlying 2-point velocity estimate is noise-dominated on this data (moves the prediction *closer* to the next real detection only 30.5% of the time). Widening the gate based on that same noisy speed estimate reduces fragmentation but also lets in a few incorrect associations it previously would have correctly rejected. **This is why the recommended next step is fixing the velocity estimate's noise (e.g. reusing the per-track UKF/CTRV smoothing already built for Step 4/5, rather than a 2-point finite difference) before tuning the gate further** — a wider gate on a bad estimate is a partial fix, not a complete one. Noted here as the natural follow-up, not implemented as of this investigation.

### Follow-up: R mis-tuning check, and the dilution anomaly resolved

Two further checks were run on the fused-accuracy gap (fused still trailing LiDAR/camera individually), following the same "verify against real data before changing anything" discipline as above.

**R was genuinely mis-tuned in one place, fixed in two passes.** `Step_4_Fusion.ipynb`'s per-sensor UKF smoothing (`smooth_track_states()`, which runs *before* any cross-sensor merge) used one fixed `R = np.diag([0.5, 0.5])` for LiDAR, radar, and camera alike, while Step 5's own per-dataset UKF already derived sensor-specific `R` from `SENSOR_TRUST_WEIGHT`. `SENSOR_TRUST_WEIGHT` was moved to `config.py` as a single shared source (Step 4's smoothing, Step 4's merge weighting, and Step 5's UKF all import it now, instead of three independent copies that could silently drift apart — the same failure class this pipeline already hit twice with radar's `dyn_prop`/velocity fields and the `["points"]` unwrap).

*Pass 1 — propagate the existing assumed weights, unchanged (lidar 44, radar 4, camera 1.0).* A controlled Kalman-gain comparison (same predicted state/covariance, only R varied) confirmed the fix behaves as intended: LiDAR's gain went 0.864→0.993 (trusts new measurements far more), camera's 0.864→0.760 (trusts them less). But fused MAE/RMSE moved slightly the *wrong* direction: 3.82→3.84 / 8.11→8.18 (Good_pct 49.6→49.8). Before assuming the fix itself was the problem, camera's assumed σ≈1.0m was checked for staleness (git history: both it and Step 2.3.1's LiDAR-depth-borrowing landed in the same initial commit, so it isn't outdated) and measured directly against ground truth: median 1.487m — *higher* than assumed, no case for lowering it at that point.

*Pass 2 — actually measure the variance, per-sensor, with a methodology check first.* Matched-track position vs. `sample_annotation` ground truth, MAD-based robust sigma (insensitive to a small fraction of mismatches). Camera: measured var 0.81 (94.8% inlier rate — trustworthy, well-formed tracks). Camera-mono: measured var 1.70 (95.0% inlier — also trustworthy; wasn't even in `SENSOR_TRUST_WEIGHT` before, silently defaulting to camera's trust level via a fallback and understating its real, worse noise). **LiDAR and radar could not be measured this way and were left at their assumed values (0.0225, 0.25)** — their much higher track fragmentation (4.1x/2.4x vs. camera's near-1x) means enough short tracks lock onto the *wrong* nearby vehicle in dense traffic that only ~86% of matched points are real inliers, not the >97% a robust estimator needs; even the *median* came out ~2.0m, physically impossible for LiDAR, proving this isn't a small-tail-outlier problem robustness could fix. Using that measurement would have made LiDAR/radar *less* trusted than the existing assumption, contradicting known sensor physics — a genuinely separate finding in its own right (fragmentation doesn't just hurt accuracy, it actively corrupts the ability to calibrate the pipeline that would fix it), not a failure of this fix.

Updated `SENSOR_TRUST_WEIGHT = {"lidar": 44.0, "radar": 4.0, "camera": 1.23, "camera_mono": 0.59}` (weights — `R = 1/weight` downstream, so camera's R became 0.81 and camera-mono's 1.70, verified numerically via the same Kalman-gain check using the real `config.py` values, not a hand-recomputation). One claimed "reciprocal inversion bug" was raised and checked directly against the code and a live numeric run — `R_camera` computed out to 0.813 and `R_camera_mono` to 1.695, both matching their measured variances almost exactly, confirming no inversion; camera-mono correctly ends up *less* trusted than camera (lower weight), not more. **Result: fused MAE 3.84→3.81, RMSE 8.18→8.12, Good_pct 49.8→50.1** — a small but genuine improvement, now that the correction is measurement-based rather than guessed, and confirmed not to be a formula error.

**The "long tracks are worst" dilution anomaly is real but was overstated by outliers, confirmed via per-track breakdown, and survived both R passes unchanged.** Bucketing fused's matched TTC points by track length (short <5 pts, medium 5-19, long 20+) showed medium best (MAE 3.04-3.17 across all three R settings tried) and long *worst* (5.33-5.96) — the opposite of what simple "young unconverged tracks drag the average down" dilution would predict. Breaking the long tracks down individually: median per-track MAE (~6) is close to the bucket average, but the *mean* (~12-13) is dragged up hugely by 6 tracks with only 1-4 matched points each and individual errors of 24-48s — these are long tracks (20+ total frames) that only briefly, sparsely locked onto ground truth, and that handful of isolated bad matches dominates the point-weighted bucket average. A robust check confirms it: **median point-error by bucket is consistently short≈1.2, medium≈0.8, long≈1.2** across all three R settings — under a statistic outliers can't dominate, "long is worst" mostly disappears; medium remains best but long is comparable to short, not catastrophic. The anomaly survived both the flat-weight R fix and the measured-variance R fix unchanged in shape, confirming it's fully independent of R-tuning — a small number of long tracks with sparse bad ground-truth locks, not a systematic long-track degradation or an R symptom.

### Verified correct (no bug found) — three checks worth recording so they aren't re-litigated

- **`centroid_to_global()` runs before tracking, not after.** Step 3.1's main loop builds `detections_global` via `centroid_to_global(...)` for every cluster, then passes that already-global list into `tracker.update()` — confirmed by reading the cell directly. Centroids are never in raw sensor-local frame (~1.8-2m above ground) when the tracker sees them.
- **Scene-boundary tracker resets are verified on real data, not just present in code.** Beyond `GlobalFrameTracker` checking `scene_name` on every update (documented above), Step 3.1's own `assert len(cross_scene_associations) == 0` runs against the real 404-sample/10-scene dataset on every execution and has passed every single run in this project's history — a violation would crash the notebook, which would have been visible.
- **TTC's sign convention for radar is correct, and the specific failure mode described doesn't structurally exist.** Radar's raw Doppler `relative_speed`/`vx`/`vy` fields are parsed and stored (Step 1.2/2.2) but never consumed by Step 5's TTC computation — grep-confirmed zero references. Radar tracks are plain `(sample_id, timestamp, [x,y,z])` position tuples, same as LiDAR; TTC velocity always comes from position deltas (UKF or finite-difference), never a raw sensor-reported speed with its own sign convention. Traced one real closing radar object (`track_035fae91`) through the actual formula: `closing_speed` is correctly positive (6.94→6.92→5.01 m/s) while distance shrinks (31.72→28.32→23.65m), giving sensible finite TTC (4.57s→4.09s→4.72s); once the object's own motion changed and it was no longer closing, `closing_speed` correctly went negative (-0.80) and `ttc` correctly became `inf` rather than a nonsensical negative or inverted value.
